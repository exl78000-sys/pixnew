# 進球細節:規格、排版與 AI 助手提示詞

> 目標:球隊詳情頁能回答「這一季進了幾球、對哪一隊進的、誰進的、誰助攻、
> 先發還是替補進的、第幾分鐘進的」。
>
> 分兩階段。**階段一先做**(一次下載三個靜態檔就拿到兩季完整資料),
> 階段二已改成由既有排程順手累積,**零額外請求**。
>
> 這份文件的用途:把「需要連外網」的抽取工作分出去給 AI 助手做,
> 抽完的結果交回來,對照與前端由本專案接手。
>
> **抓取量請先看第〇節。** 三條路徑的「會不會被擋」完全不是同一件事。

---

## 〇、抓取風險分級(先看這個)

「會不會被擋」對三條路徑完全不是同一件事:

| 路徑 | 請求量 | 對象 | 風險 |
|---|---|---|---|
| 階段一 merged_gw | **一季 3 個檔** | raw.githubusercontent.com | **沒有**。下載靜態檔,不是爬網站 |
| 階段二 官方進球事件 | **0 個額外請求** | — | **沒有**。見下方說明 |
| Understat 球隊季摘要 | **每季 20 個,只抓一次** | Understat JSON 端點 | 低頻率單線、已快取、可續跑 |

**階段二為什麼是零額外請求:**
本專案的排程本來就每天在打 `pulselive /fixtures/{id}` 抓正式陣容
(`fetch-official.mjs`,每次執行上限 14 場、已完賽的抓過就不再抓)。
同一個回應裡本來就帶著 `events`,我們以前只讀 `teamLists`,其餘欄位全丟掉了。
現在改成順手存下來 —— **一個新請求都不用發**,而且隨賽季自動累積。

所以原本規劃的「一場一個請求、一季 380 次」補抓完全不需要。
往季(2024-25、2025-26)先沒有進球事件 —— 但那兩季的**進球與助攻仍然有**
(走階段一的 merged_gw),少的只是「第幾分鐘」與「誰助攻哪一球」。

### 「進球方式」資料源的實測結果

2026-08-25 實跑 `npm run probe:events`(刻意只打 2 個請求):

- **StatsBomb Open Data**(GitHub 靜態 JSON,完全沒有被擋的問題):
  英超只有 **2015/2016 與 2003/2004** 兩季。2023 年以後開放的是德甲、Ligue 1、
  Euro 2024、Copa America、女足各聯賽等等 —— **現行英超不在裡面**。
  它的商業 API 是企業級定價,跟 Opta 同一個量級,MVP 不考慮。

- **Understat**:初次只看 HTML 時找不到舊版的內嵌 JSON;後續確認改版後由
  `GET /getTeamData/{team}/{season}` 載入。每隊一個摘要請求就有
  OpenPlay / FromCorner / SetPiece / DirectFreekick / Penalty 的射門、進球、xG 與對手數據。
  `scripts/fetch-setpieces.mjs` 已以 1.6 秒間隔單線抓取,每隊存 checkpoint,失敗可續跑。
  20 隊五類進失球總和都必須跟 openfootball 比分對上,才會標成完整。

**結論:球隊整季分類可做,且已做;單一進球的球員級分類仍不做。**

檔案實測大小:`2024-25/gws/merged_gw.csv` 27,606 列 × 49 欄、
`2025-26/gws/merged_gw.csv` 29,758 列 × 46 欄。`2026-27` 還沒發布(HTTP 404),
本季要靠專案自己每天存的 `data/raw/season-gws.json` 累積。

官方 events 的實際長相(Fulham vs Chelsea,5 顆進球):

```json
{ "id": 183587, "personId": 72371, "teamId": 4, "assistId": 49293,
  "clock": { "secs": 60, "label": "01'00" }, "phase": "1",
  "type": "G", "description": "G",
  "score": { "homeScore": 0, "awayScore": 1 } }
```

事件型別代碼:`PS` 半場開始、`G` 進球、`B` 出牌(`description` 是 `Y`/`R`)、
`S` 換人(`description` 是 `ON`/`OFF`)、`PE` 半場結束。

## 二、階段一的輸出規格

每季一個檔:`epl/data/raw/fpl/{season}-goals.json`

```json
{
  "_season": "2025-26",
  "_source": "https://raw.githubusercontent.com/vaastav/Fantasy-Premier-League/master/data/2025-26/gws/merged_gw.csv",
  "_generatedAt": "2026-08-25T00:00:00Z",
  "_counts": {
    "csvRows": 29758,
    "records": 1042,
    "goals": 1116,
    "assists": 812,
    "ownGoals": 41,
    "unmatchedNames": 0,
    "scoreMismatches": 0
  },
  "records": [
    {
      "code": "223340",
      "team": "ARS", "opp": "COV", "home": true,
      "round": 1, "date": "2025-08-15",
      "min": 90, "start": true,
      "g": 1, "a": 0, "og": 0, "pm": 0
    }
  ]
}
```

欄位定義:

| 欄位 | 意義 | 型別 |
|---|---|---|
| `code` | 球員代碼。**取自 `players_raw.csv` 的 `code` 欄,不是 `element`** | 字串 |
| `team` / `opp` | 三碼隊伍代碼(ARS/COV/…) | 字串 |
| `home` | 該球員的球隊是否主場 | 布林 |
| `round` | 第幾輪 | 整數 |
| `date` | 開賽日期(從 `kickoff_time` 取 `YYYY-MM-DD`) | 字串 |
| `min` | 該場上場分鐘 | 整數 |
| `start` | 是否先發(`starts == 1`) | 布林 |
| `g` / `a` / `og` / `pm` | 進球 / 助攻 / 烏龍球 / 十二碼未進 | 整數 |

**只輸出 `g + a + og + pm > 0` 的列。** 29,758 列裡絕大多數是 0,全存會讓檔案
從 100 KB 變成 6 MB,而多出來的那些列一個問題也回答不了。

## 三、四個對照陷阱(做錯了不會報錯,只會靜靜給出錯的答案)

### 1. `element` 是「每一季重新編號」的,`code` 才是跨季穩定的鍵

`merged_gw.csv` 的 `element` 是那一季的 FPL 內部編號。
同一位球員在 2024-25 是 328、在 2025-26 可能是 412。
本專案的球員鍵是 `players_raw.csv` 的 **`code`**(Raya 在兩季都是 `154561`)。

→ **必須用同一季的 `players_raw.csv` 建 `element → code` 對照表。**

### 2. `opponent_team` 是「每一季重新編號」的隊伍 id

FPL 的隊伍 id 是該季 20 隊按英文名排序給的 1~20。
2025-26 的 `3` 是 Burnley;2024-25 的 `3` 是別隊(那季沒有 Burnley)。

→ **必須用同一季的 `teams.csv` 建 `id → short_name` 對照表。**
已驗證 `short_name` 與本專案的隊伍代碼 20 隊完全一致,可以直接用。

### 3. **球員所屬隊伍不能取自 `players_raw.csv`**(這一條是我原本寫錯的)

第一版規格叫協作方從 `players_raw.csv` 取 `team`。**那是錯的** ——
`players_raw.csv` 是**季末快照**,球季中途轉隊或外借的人會掛在最後那一隊。

實例:Rashford 在 2024-25 第 13 輪替曼聯進了 2 球,但他一月外借維拉,
季末快照把他記在維拉 —— 那兩球就變成「維拉在 MUN 4-0 EVE 那場進的」。
**而且不會報錯**,只是靜靜把球記到錯的隊上。實測交回來的檔案有 10 + 26 筆這種錯。

正確做法:**根本不需要 team 欄**。`opponent_team` 與 `was_home` 都是逐場欄位、
兩個都對,知道「對手是誰、我方是主是客、哪一天」就能從賽程反推我方是誰 ——
那一天對手只打一場,我方就是那場的另一邊。本專案的 adapter
(`scripts/lib/adapters/fpl-goals.mjs`)在載入時就是這樣修的,所以**這份檔案
即使 team 欄是錯的也還能用**,不必重抓。

配對用**日期優先、輪次備援**:FPL 的 `round` 是 gameweek,改期的比賽會跟賽程
的輪次對不上(實例:AVL vs LIV 在 FPL 是 GW25、在賽程是第 29 輪,但日期一樣)。

### 4. `name` 欄的格式在不同賽季不一樣

較早的賽季用 `First_Second_id` 這種底線格式,較新的用 `First Second`。
**不要用名字當鍵。** 名字只在對不上 `element` 時拿來人工核對。

## 四、自我檢查(請務必跑,並把結果寫進 `_counts`)

1. **對不上的 `element`**:每一列的 `element` 都要在該季的 `players_raw.csv`
   裡找得到。找不到就記進 `unmatchedNames`,並在報告裡列出前 10 個名字。
   正常情況這個數字應該是 **0**。

2. **比分核對**:對每一場比賽,
   `該隊球員 goals_scored 總和 + 對手球員 own_goals 總和` 必須等於該隊的實際比分
   (`team_h_score` / `team_a_score`)。
   對不上的場次數記進 `scoreMismatches`,並列出前 5 場。
   **正常情況應該是 0** —— 本專案已用 2026-27 第 1 輪驗證過這條規則成立
   (29 顆球員進球 + 1 顆烏龍球 = 賽果總和 30)。

3. **總數合理性**:一季英超約 1,000~1,200 顆進球。
   `_counts.goals` 明顯偏離這個範圍就是哪裡錯了,先別交,回頭查。

## 五、排版規格(球隊詳情頁)

在「教練」區塊之後、「開季賽程」之前,新增一段 `<h2>進球來源</h2>`,
內含四個面板。**標了「階段二」的面板在階段一先不做,不要放空殼。**

### 面板 1 — 對手分佈(階段一)

橫向長條,一列一個對手,依進球數排序。
每一列同時顯示「對他進幾球 / 被他進幾球」,用兩條反向的條。

- 條的顏色:本隊用本隊的 `chartColor`,對手用中性灰(`--ink-3`)。
  不要用對手的隊色 —— 20 隊一起出現時會變成彩虹,反而看不出重點。
- 沒交手過的隊伍不列(升班馬)。
- 下方一行說明:資料涵蓋哪一季、共幾場。

### 面板 2 — 進球榜與助攻榜(階段一)

兩欄並排的表格,各取前 8 名。欄位:球員、進球(或助攻)、每 90 分鐘、
先發/替補進球拆分。

- 「每 90 分鐘」要標明分母是上場分鐘,不是出賽場次。
- 出場不足 450 分鐘的球員,per-90 欄顯示 `—` 而不是一個會誤導人的大數字
  (這是本專案既有的 `QUALIFY_MINUTES` 規則,沿用)。

### 面板 3 — 先發 vs 替補(階段一)

一組對照數字:先發進球 N 球(佔 x%)、替補進球 M 球(佔 y%)。
下方一句話說明替補進球佔比的聯盟平均是多少,讓讀者知道這隊算高還是低。

### 面板 4 — 進球時間分布(**階段二**)

橫軸切成 6 段(0-15、16-30、31-45、46-60、61-75、76-90+),
縱軸是進球數與失球數。加時與傷停併入該半場的最後一段。

需要官方 events 的 `clock`,階段一做不到 —— **階段一不要放這個面板,
也不要放「資料準備中」的佔位**,沒有就是沒有。

### 共通規則

- 每個面板都要標明**資料涵蓋哪些賽季**。兩季完整、本季只有幾輪,
  這件事必須寫在畫面上,不能讓讀者自己猜。
- 球員的逐球表不要留「進球方式」欄位;球隊整季分類放在獨立的「上季進球方式」面板。

## 七、提示詞 A —— 階段一:逐輪進球助攻抽取

> 把 `---` 之間整段複製給 AI 助手。它需要:能連外網、能跑 Node 或 Python。

---

### 任務

從公開的 FPL 資料鏡像抽取英超兩個賽季的**逐場進球與助攻紀錄**,
產出兩個 JSON 檔。

### 輸入(全部公開,不需要金鑰)

基底網址:`https://raw.githubusercontent.com/vaastav/Fantasy-Premier-League/master/data`

每個賽季(`2024-25`、`2025-26`)要下載三個檔:

```
{base}/{season}/gws/merged_gw.csv     逐輪 × 逐球員(主檔)
{base}/{season}/players_raw.csv       球員名冊(拿 element → code 對照)
{base}/{season}/teams.csv             隊伍名冊(拿 id → short_name 對照)
```

實測大小參考:2024-25 的 merged_gw 有 27,606 列、2025-26 有 29,758 列。
數量差太多就是抓錯檔了。

### 四個一定要做對的對照(做錯不會報錯,只會給出錯的答案)

1. **`element` 每季重新編號。** `merged_gw.csv` 的 `element` 是該季的內部編號,
   同一位球員不同季編號不同。輸出必須用 `players_raw.csv` 的 **`code`** 欄
   (跨季穩定,例如門將 Raya 兩季都是 `154561`)。
   → 用**同一季**的 `players_raw.csv` 建 `id → code` 對照表。

2. **`opponent_team` 也是每季重新編號**(1~20,依該季 20 隊英文名排序)。
   → 用**同一季**的 `teams.csv` 建 `id → short_name` 對照表。
   `short_name` 就是我要的三碼代號(ARS、LIV、MUN…),直接用,不用再轉。

3. **球員所屬隊伍不要取自 `players_raw.csv`。** 它是季末快照,
   球季中途轉隊或外借的人會掛在最後那一隊,他早期替舊東家進的球會被記到新東家。
   用 `merged_gw.csv` 自己的 `team` 欄(逐輪的),沒有就填 `null`。

4. **不要用 `name` 欄當鍵。** 它的格式在不同賽季不一樣(有的用底線串接 id)。
   名字只在對不上時拿來人工核對。

### 輸出格式(請嚴格照這個結構)

檔名 `{season}-goals.json`,例如 `2025-26-goals.json`:

```json
{
  "_season": "2025-26",
  "_source": "<你實際下載的 merged_gw.csv 網址>",
  "_generatedAt": "<ISO 8601 時間>",
  "_counts": {
    "csvRows": 29758, "records": 1042, "goals": 1116, "assists": 812,
    "ownGoals": 41, "unmatchedElements": 0, "scoreMismatches": 0
  },
  "records": [
    { "code": "223340", "team": "ARS", "opp": "COV", "home": true,
      "round": 1, "date": "2025-08-15", "min": 90, "start": true,
      "g": 1, "a": 0, "og": 0, "pm": 0 }
  ]
}
```

- `code`:字串(不要轉成數字,前導零會掉)
- `team`:該球員所屬隊伍的三碼代號。**注意:不要用 `players_raw.csv` 的 `team` 欄** ——
  那是季末快照,球季中途轉隊或外借的人會掛在最後那一隊(實測有幾十筆這種錯)。
  用 `merged_gw.csv` 自己的 `team` 欄(逐輪的);如果那一季沒有這一欄,
  就填 `null`,我這邊會從對手與主客反推 —— 寧可留空也不要填一個錯的。
- `opp`:對手三碼代號
- `home`:`was_home` 轉成布林
- `date`:從 `kickoff_time` 取 `YYYY-MM-DD`
- `start`:`starts == 1`
- `g`/`a`/`og`/`pm`:`goals_scored` / `assists` / `own_goals` / `penalties_missed`

**只輸出 `g + a + og + pm > 0` 的列。** 絕大多數列全是 0,
全存會讓檔案從 100 KB 變成 6 MB,而且一個問題也回答不了。

### 上線後立刻抓到的一個錯

第一版是用 `type === 'G'` 過濾的。排程跑完、資料進來之後對一次帳就露餡了:
**Brighton 4-0 Aston Villa 只存到 3 顆**,少的第一顆是**烏龍球** ——
烏龍球在官方的事件流裡不是 `G`,是另一種型別。

改成**「比分變了就是進球」**判定:官方每一筆事件都帶著當下比分
(而且是該事件發生**之後**的比分,已用 FUL 2-3 CHE 的五顆逐筆核對),
比上一筆高就代表中間發生了一顆進球,不管它叫什麼名字。
這樣不需要事先集滿所有型別代碼,新的代碼出現也不會漏。

得分方也由比分差決定,**不看 `teamId`**。實測過一例:Lindelöf(維拉)踢進烏龍球,
那筆事件的 `teamId` 是 131(Brighton),也就是**得分方**——
但樣本只有一顆,反過來當通則一樣沒有根據。結論是 `teamId` 的語意不明確,別依賴它。

子類型已經確定(2026-08 更新,原本這裡寫「還沒集滿,不要做」):

> 10 場 30 顆進球裡出現三種 `description`:`G` 28 顆(一般)、`P` 1 顆(十二碼)、
> `O` 1 顆(烏龍球)。`O` 用名單核對過 —— 踢進去的人在對方名單裡。
> 這三種已經在前端顯示(單場分析頁的進球時間軸)。
