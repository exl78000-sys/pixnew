# 賽事自動更新：故障處理

## 現行資料路徑

英超即時比分由 FPL 流程提供；官方陣容、陣型、進球、牌與換人事件由
`scripts/fetch-official.mjs` 讀取 PulseLive。原始快取寫入
`data/raw/pulselive/official.json`，建置後再轉成 `web/data/official.json`。

平日完整建置由 `.github/workflows/epl-live.yml` 執行；比賽中的高頻更新由
`.github/workflows/epl-matchday.yml` 在單一 job 內每兩分鐘輪詢。GitHub 排程只負責啟動，
不是精準計時器。

## 2026-08-31 故障紀錄

症狀是原始資料已更新，但 GitHub Pages 沒有發布新版。Actions 的抓取、建置與資料回寫成功，
`npm test` 在「正式資料每一顆進球都查得到射手」失敗，因此後續打包與 Pages 部署被跳過。

問題場次是 `CHE|BHA`（Chelsea 4–3 Brighton，fixture 128935）。90+6 分的最終比分
同時出現在兩筆事件：

- `PE`：完場標記，沒有 `personId`。
- `G`：真正進球，`personId` 22542（Pascal Groß）。

`PE` 的 `time.millis` 稍早，舊解析器以事件寫入時間逐筆掃描，讓 `PE` 先認領 4–3 的比分變化；
後面的 `G` 因比分不再變化而被忽略。舊快取規則又把所有完賽資料永久視為定案，所以無法自癒。

## 已實作修復

`goalsOf()` 仍以比分變化判定進球，避免漏掉非 `G` 型別的烏龍球；但同一比分有多筆事件時：

1. `B`、`S`、`PS`、`PE` 不得認領進球。
2. 優先採用有 `personId` 的真正進球事件。
3. 優先次序相同時才使用事件時間排序。
4. 找不到可信進球事件時保留空值，交由品質檢查重抓，不把牌、換人或完場事件誤當射手。

完賽快取必須同時符合以下條件才停止更新：

- 進球事件數等於主客最終比分總和。
- 最後一筆進球帶出的比分等於最終比分。
- 每一顆進球都有 `personId`。

不完整資料依序延遲 2 分鐘、10 分鐘、30 分鐘、2 小時、12 小時重抓；之後維持每 12 小時重試。
狀態記在該場 `quality`：`complete`、`issues`、`retryCount`、`nextRetryAt`、`checkedAt`。

## 檢查與恢復

在 `epl/` 執行：

```bash
npm run official       # 補抓缺失或品質不完整的官方場次
npm run laliga:build   # 先建立西甲資料
npm run en2:build      # 再建立英冠資料
npm run build          # 建立英超資料並統一資產版本戳
npm test               # 完整資料與程式檢查
```

若 `official` 顯示 `待重試`，查看該場 `quality.issues`：

| 代碼 | 意義 |
|---|---|
| `missing-final-score` | 賽程端沒有可辨識的最終比分 |
| `goal-count-mismatch` | 進球事件數與比分總和不同 |
| `score-mismatch` | 最後進球事件的比分不是最終比分 |
| `missing-scorer` | 至少一球沒有射手 id |

需要跳過退避時間立即重抓全部完賽快取時，可執行 `npm run official -- --all`。這會增加官方端點請求量，
只應用於格式遷移或確認上游已修正時。

## 後續架構方向

目前先修復靜態站與 Actions 流程，不進行前後端重寫。下一階段建議採混合式架構：保留靜態前端與
歷史分析快照，只把即時抓取、重試、品質狀態與最新資料 API 移到小型後端。實作前必須另寫架構決策，
記錄平台、資料庫、成本、回復方案與遷移順序。
