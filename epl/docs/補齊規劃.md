**根源**:西甲的 `meta.edition === 'basic'`,`page-teams.js` / `page-index.js` /

所以現在補一個區塊要在兩個地方各寫一次,而且兩邊排版本來就長得不一樣 ——
這正是「西甲想以英超為模板」要解的問題。**方向:讓 basic 分支逐步退場,
改成共用英超版面,每個區塊自己判斷資料在不在。** 不要再往 basic 分支加東西。

## 模型本身(最難的一項)

英超 RPS 0.2076 對收盤盤口的 0.2051 —— **仍然輸給市場 0.0025**。

**上一季的定位球強弱**、**賽程密度**。五個都在雜訊範圍內,係數維持 0,
`npm test` 有一條守著。模型頁把每一個的假說、做法與數字都攤開來。

還沒試過、而且資料已經有的方向:
- ~~**進球情境**~~ —— **2026-08-27 測完,沒通過。** 假說是「定位球能力比運動戰
  更能跨季延續」,用上一季的定位球進失球當先驗(十二碼不算)。
  調參 2024-25(先驗 2023-24)、驗收 2025-26(先驗 2024-25)。
  驗收基準 RPS 0.20761,三組係數全部在雜訊範圍內(最好的一組 −0.00005,±0.00011)。
  **關鍵在於連調參賽季都幾乎挑不出改善**(0.20131 → 0.2013)—— 調參可以盡情挑,
  連挑都挑不到,代表訊號真的不存在。合理解釋:定位球得分能力本來就已經反映在
  Dixon-Coles 的攻守參數裡,單獨拉出來沒有多給模型資訊。
  結果存在 `data/situation-tuning.json`,模型頁有一整段攤開來(`npm run tune:situations` 可重跑)。
- ~~**賽程密度**~~ —— **2026-08-27 測完,沒通過,但這一個的失敗方式比較有意思。**
  驗收三組全在雜訊內(最好的 −0.00038,±0.00042)。**關鍵是係數方向跟假說相反**:
  調參挑出 bRest=−0.25(休得越多、進球期望越低)、bOpp=+0.2。疲勞假說預期的是反過來。

  而打歐戰的正好是強隊,所以係數抓到的是實力不是疲勞。
  **量測缺陷要記住**:歐冠、歐霸與盃賽都不在賽程資料裡,所以有打歐戰的球隊
  休息天數是系統性高估。沒通過只代表「用聯賽日期算出來的密度沒有預測力」,
  **不代表賽程密度沒有影響**。要真的測,得先有跨賽事的完整賽程。

## 已經試過而不通的路(不要重跑)

寫在這裡是為了讓下一個人不必重走一遍死路。每一條都是實測,不是推測。

### API-Football:Free 方案不含本季與上季

```
GET /status → 方案:Free・今日請求 0/100
GET /fixtures?league=140&season=2026&status=FT-AET-PEN
GET /players?league=140&season=2026&page=1
→ 200 {"errors":{"plan":"Free plans do not have access to this season,
        try from 2022 to 2024."}}
```

`league=140` 的 2025 與 2026 兩季**完全拿不到**。不是額度問題,是方案不含這些賽季。
西甲 API-Football 備援賽後資料目前 `0/16`；同樣不是還沒抓到,而是方案不含 2025/26、2026/27。SportMonks 已依方案能力探測取得 16/16 場，兩者不可混為同一個缺口。
SportMonks 名單、賽程與允許的 Fixture 詳情 include 已可讀；`xGFixture` 單項回 HTTP 403／5002，代表該加購未包含，不是整個 Fixture 詳情不可用。

換一個涵蓋本賽季的方案之後**程式會自己恢復**:抓取端撞到 plan 錯誤時把原因寫進
賽後存檔的 `blocked`,拿得到清單就清掉。build 與前端都照它說的講,不必改碼。

重跑探測:`npm run probe:laliga-players`(硬上限 5 個請求)。

### Understat:資料不在 HTML 頁裡

```
GET understat.com/league/La_liga/2025     → 200 但只有 18 KB,一個資料變數都沒有
GET understat.com/team/Arsenal/2025       → 同上
GET understat.com/getLeaguePlayers/La_liga/2025 → 404(這個路由不存在)
```

**能用的是獨立的 XHR 端點**:

```
GET  understat.com/getTeamData/{隊}/{年}          → 球隊整季(進球情境就是這裡來的)
POST understat.com/main/getPlayersStats/
     body: league=La_liga&season=2025            → 整季 600 名球員,一個請求
```

找到第三個的關鍵:不帶參數打 `main/getPlayersStats/` 回的是
`{"error":{"error_code":4}}` —— **回結構化錯誤而不是 404,代表端點在、只是少參數**。
在前兩個候選就下結論「Understat 拿不到球員資料」就會錯過。

重跑探測:`npm run probe:laliga-playerdata`(硬上限 6 個請求,單線間隔 1.5 秒)。

## 不做的事(同樣重要)

- **單一進球的球員級「進球方式」** —— Understat 給的是球隊整季摘要,
  把某一類掛到某位球員的某一顆球是我們沒有的資料。球員逐球表不要加那一欄。
- **把沒通過驗收的特徵放進模型** —— 近五戰與交手紀錄的係數是 0,
  `npm test` 有一條專門守著。直覺上該有用不是理由。
- **大量爬網站** —— 靜態檔下載沒問題,官方進球事件是零額外請求。
  一場一個請求的做法先不要做。探測腳本自己也有請求硬上限。
- **為了畫面好看補測試資料** —— 要真實數字就在有 Secret 的 runner 上跑,
  不要寫假資料進正式快取。
- **拿賽後重建的模型冒充賽前預測** —— 沒有賽前快照的場次,`prediction` 就該是 `null`。
- **留一個永遠空白的欄位** —— 比不做更糟,讀者會以為是壞掉。
  拿不到就在畫面上說拿不到,並說明是「拿不到」還是「還沒到」。
