### 已完成：人工整理外電可累積（收件匣 → 檔案庫）

`data/manual/news-curated.json` 是協作方每次交付的整份檔案，一份只涵蓋一週。
直接讀它的話，下一次交付會把上一週整批蓋掉，**而且不會有任何地方報錯**。
現在它只當收件匣，由 `npm run news:merge` 併進 `data/manual/news-curated-archive.json`：
依 `id` 去重、記 `firstSeen`／`lastSeen`、淘汰 180 天前的；同一個 id 再送一次算更正，
內容會更新但 `firstSeen` 保留。內容沒變就不寫檔，所以掛在每 10 分鐘的排程上不會產生雜訊提交。

`build` 讀的是**檔案庫疊上收件匣**（同一個 id 以收件匣為準），新交付一落地就看得到，
不必等合併那一步。轉換邏輯收在 `scripts/lib/curated-archive.mjs` 的 `loadCurated()`，
英超與西甲各呼叫一次同一個函式。

涵蓋範圍在動態頁上照實講：把每次交付的 `window` 合成連續區間，
**中間沒交付的那幾段列成斷檔**（「那幾天不是沒有新聞，是本站沒有收」）。
交付格式見 `docs/外電整理-交付格式.md`。

## 兩條在階段之外的管線(2026-08-28 新增)

這兩條不屬於「西甲補到跟英超一樣」那條主線,但都會影響全站,所以列在這裡。

### Obsidian vault —— 資料集的筆記版

`npm run obsidian` → `epl/vault/`,5,675 則互相連結的 Markdown。
比照 `dist/` 是**產物**、不進版控,但 `vault/我的筆記/` 是使用者手寫的,
`.gitignore` 特地留了 `!epl/vault/我的筆記/`,產生器也永遠不碰那個資料夾。

已掛進 `npm run local:sync`(vault 是本機資產,**不放 CI** ——
在 runner 上產生一份沒有人看得到的筆記沒有意義)。

寫檔前兩道守門,不通過就中止而且一個檔案都不寫:同檔名、壞連結。
細節與「這裡刻意不做的三件事」見 `docs/接手資訊.md`。

### 租借紀錄 —— 人工交付必須先過核對器

```
data/manual/loans.json      收件匣(交付的原始內容)
  ↓ npm run loans:verify    ← 已掛進 local:sync 與 epl-live.yml
data/loans-verified.json    產物
  ↓ scripts/lib/loans.mjs   兩個 build 各呼叫一次同一支
players.json 的 loans[]  →  網站與 vault
```

**收件匣改過但沒重跑核對會被擋下來。** 產物記著收件匣的 sha256,
`loadVerifiedLoans` 比對不上就回 `stale` —— build 整批不掛並印出原因,
`npm test` 那條也會紅。沒有這道守門的話,build 會拿舊的核對結果背書新的交付內容,
而且不會有任何地方報錯。**兩種狀態都實測過會擋。**

判定分四級(confirmed / consistent / contradicted / block-suspect / unverifiable),
發布只有前兩級,而且等級要跟著資料走到畫面上 ——
「有獨立來源確認」與「只是沒查到矛盾」對讀者的意義不同。

### 第一原則:它是遊戲,跟站上的預測是兩條管線

這一條是使用者定的,也是整份規劃的地基。**模擬遊玩讀真資料,但不寫回任何真資料,
它算出來的機率不是本站的預測。** 具體的隔離:

| 層 | 真實管線(現有) | 模擬遊玩(新) |
|---|---|---|
| 程式 | `scripts/build.mjs`、`scripts/lib/`、`web/assets/js/predict-core.js` | `scripts/game/`、`web/assets/js/game/` —— **只 import 真實管線,真實管線不 import 它** |
| 產物 | `web/data/*.json` | `web/data/game/*.json` |
| 機率 | Dixon-Coles + Elo,走查回測、golden 守等價 | **遊戲模型**:以站上預測為錨,依名單 / 陣型 / 紅牌相對調整 |
| 使用者的操作 | 無 | 換人、改陣型 —— 只存在瀏覽器裡(跟「我的預測」同做法),不進資料、不進 vault |
| 畫面上的標示 | 「本站預測」 | 「**遊戲模型,不是本站預測**」;每個面板標 真資料 / 抽樣 / 遊戲規則 / 演出 |

測試要守四件事,缺一個這條隔離就是空話:(1) 有沒有跑 game build,真實產物**逐位元相同**;
(2) `scripts/lib/`、`build*.mjs`、`predict-core.js` 沒有任何一行 import `game/`;
(3) golden(前端預測核心 = lib 模型)不動;(4) 遊戲模型在**沒有任何改動**時,
機率要等於站上該場預測 —— 錨定不成立的話「相對調整」就沒有參照點。

為什麼可以這樣做而不違反鐵則二:鐵則二管的是**本站的預測模型**不能放沒回測的特徵。
遊戲模型不是預測、不對外宣稱準度、不進模型頁,而且畫面上寫明是遊戲規則。
但鐵則一(不准編數字)照樣管它:**每個係數要嘛從資料算,要嘛標成「遊戲規則」並寫出公式**,
不可以有第三種。

3. FM24 的 2D 畫面好看在**面板、事件流、畫面三者對得起來**,不在點的貼圖。

### 第 1 項:換人、時間、陣型,以及「改了以後機率怎麼變」

**能改什麼**(只能從真資料的清單裡挑,不能自由填):
- 先發與替補:從該隊本季名單挑(`players.json` 該隊球員,傷停的標出來但不禁止 —— 是遊戲);
- 陣型:只能從 `shapes.official.used`(本季用過的)加 `lineups.shape`(推估先發用的)裡挑;
- 換人:暫停後指定誰上誰下、或事先排好「第 N 分鐘換誰」;沒排的話由引擎照直方圖自動換。

**機率怎麼變 —— 遊戲模型,錨在站上預測上**:

```
λ_game = λ_site × (Q_att(現在的 XI) / Q_att(預設 XI))^a × (Q_def(對手現在的 XI) / Q_def(對手預設 XI))^(-b) × R(紅牌)
```

- `Q_att`:XI 進攻指數 = 各球員 `xgi90`(門將 0)依角色加權後相加;`Q_def`:防守指數 =
  `defCon90` + `cbi90`,門將加 `saves90`。全部是 FPL 真資料。
- **預設 XI = `lineups.json` 的推估先發**,所以沒改動時比值是 1,`λ_game = λ_site`
  —— 這就是測試(4)守的錨。
- 陣型的效果不另外加係數:改陣型會改角色格數,角色權重不同 → Q 變;
  「4-3-3 比 4-4-2 進攻」這種係數沒有資料支撐,不編。
- **`a`、`b` 是遊戲係數。** 先試著從資料校準:FPL 逐輪資料(`season-gws.json`)有每輪誰先發,
  配 2024-25 與 2025-26 的賽果,約 1,500 隊-場,用一季調、另一季驗(鐵則二的做法)。
  校準得出來就用校準值並寫出效果量與標準誤;**分不出跟 0 的差別就照實在畫面上寫
  「效果量未在資料上驗證,以下是遊戲規則」**,係數取一個寫進檔頭、有理由的值。不可以假裝校準過。
- 換人後從那一分鐘起用新的 λ_game 算剩餘期望(`inPlaySim` 本來就是分鐘制的);
  射手池、牌的候選池跟著換。

### 第 2 項:黃牌紅牌

- 犯規數抽真分布(CSV 的 HF/AF);每次犯規以該隊的「牌/犯規」比例決定有沒有牌;
  牌掛在**在場**球員上,權重用 `players.json` 該球員本季 + 上季的黃牌數(真資料),
  不再是均勻。
- 兩黃 = 紅;直接紅牌依球隊紅牌率(CSV,英超一季約 40~50 張)抽。
- **紅牌改機率**:`inPlaySim` 本來就有 `redHome` / `redAway` 參數,遊戲模型直接用它
  (`R(紅牌)`),從那一分鐘起剩餘期望改變;紅牌後那隊也少一個換人 / 射手候選。
  比分**不是**事先抽好的了 —— 見下一段。

### 比分不能再事先抽好

現在是先抽比分、再排進球分鐘、動畫照演。加了「換人改機率」與「紅牌改機率」之後,
**事先抽好的比分跟賽中改動會打架**(第 60 分鐘換上前鋒,但比分 30 分鐘前就決定了)。
所以遊戲引擎改成**逐分鐘抽**:每一分鐘依當下的 λ_game(含紅牌、換人)抽這一分鐘有沒有進球
(Poisson 分鐘制,在 `inPlaySim` 的框架裡),Dixon-Coles 的低比分修正在分鐘制下沒有直接對應,
**放棄它,並在畫面寫明「遊戲模型是分鐘制 Poisson,沒有 Dixon-Coles 修正」**。
沒有改動時,90 分鐘加總的分布跟站上預測的邊際分布一致(測試守均值與 1X2 在抽樣誤差內)。
現有的 `sampleMatch` 留給「跳到結果」以外的用途?—— 不留,**一條遊戲只能有一個抽樣方式**,
`sampleMatch` 只剩測試在用就一併退場。

### 架構:三個模組,「發生什麼」跟「怎麼演」拆開

**1. `scripts/game/build-game.mjs` + `scripts/game/lib/profile.mjs` → `web/data/game/pl.json`**

每隊一份:能力表(逐球員 Q 分量與角色)、牌權重、事件率(主客分開)、控球分布、
情境份額與各情境 xG/射門、主罰、用過的陣型、預設先發與替補席;聯賽層:換人 / 進球分鐘直方圖、
上下半場比例。**每一項附 n 與來源。** 掛在 `npm run build` 之後、`stamp-assets` 之前
(它是 pl 的產物,但戳是給 `web/*.html` 的,順序照「build 一定是最後一個」那條)。
測試:每個數字對回來源檔(Arsenal 的 sf 等於 `styleTrend.baseline.sf` 那種)。

**2. `web/assets/js/game/engine.js`(純函式、無 DOM、node 裡測得動)**

`createMatch({ profiles, home, away, seed, setup })` → 逐分鐘 `tick()`,
接受 `substitute()` / `setFormation()`,輸出事件流與當下狀態(λ_game、控球、統計)。
不變量測試:進球數 = 射門結果為進球的次數;射手都在場上;換人不超過規則;紅牌後少一人;
同種子同操作事件流逐字相同;無操作時 90 分鐘加總的 1X2 在抽樣誤差內等於站上預測。

**3. `duel-anim.js` 改成照劇本演、`duel-view.js` 改版面**

每種事件一段編排(角球、任意球、十二碼、射門與撲救、換人走場、牌);跑位、傳球、丟球的行為模型沿用。
版面照 FM24 2D classic:

```
上   記分板・時鐘・播放速度・精華模式・暫停(換人 / 改陣型在暫停時做)
中左 球場(圓點加背號、持球者名字、球、事件閃字)
中右 分頁:比賽統計 / 事件流 / 陣容與替補 / 戰術
下   動能條・文字播報(模板生成,不經 AI,每個數字來自事件流)
     「這張圖哪些是真的」圖例:真資料 / 抽樣 / 遊戲規則 / 演出
```

手機:上下堆疊。背號用 `squadNumber`(SportMonks 快取,凍結但可用)。

## 模型本身(最難的一項)

英超 RPS 0.2076 對收盤盤口的 0.2051 —— **仍然輸給市場 0.0025**。

已經量過而**沒有通過**的:近五戰狀況、近五戰進失球、歷來交手淨勝球、
**上一季的定位球強弱**、**賽程密度**。五個都在雜訊範圍內,係數維持 0,
`npm test` 有一條守著。模型頁把每一個的假說、做法與數字都攤開來。

- ~~**進球情境**~~ —— **2026-08-27 測完,沒通過。** 假說是「定位球能力比運動戰
  更能跨季延續」,用上一季的定位球進失球當先驗(十二碼不算)。
  調參 2024-25(先驗 2023-24)、驗收 2025-26(先驗 2024-25)。
  驗收基準 RPS 0.20761,三組係數全部在雜訊範圍內(最好的一組 −0.00005,±0.00011)。
  **關鍵在於連調參賽季都幾乎挑不出改善**(0.20131 → 0.2013)—— 調參可以盡情挑,
  連挑都挑不到,代表訊號真的不存在。合理解釋:定位球得分能力本來就已經反映在
  Dixon-Coles 的攻守參數裡,單獨拉出來沒有多給模型資訊。
  結果存在 `data/situation-tuning.json`,模型頁有一整段攤開來(`npm run tune:situations` 可重跑)。
- ~~**賽程密度**~~ —— **2026-08-27 測完,沒通過,但這一個的失敗方式比較有意思。**

  而打歐戰的正好是強隊,所以係數抓到的是實力不是疲勞。

### 球隊頁的數字排版

原本把多個數值壓成一條字串靠位置對應:

    勝 / 和 / 負      →  26 / 7 / 5
    進球 / 失球 / 淨勝 →  71 / 27 / +44
    前四 / 降級        →  97.5% / 0%        ← 斜線讓它看起來像分數
    上半場 進 / 失     →  30 / 10
    下半場 進 / 失     →  41 / 17

讀者要自己數到第幾個才知道是哪一項,而且三個數字常常單位還不一樣
(前兩個是次數、第三個是差值而且帶正負號)。

改成 `C.statCells()`:每個數字自己帶標籤。另外兩條規矩寫進元件裡:

- **值是 0 不上色。** 紅色的 0 會把視線引到「什麼都沒發生」那一格。
- **顏色只給狀態(勝/負),而且一定跟標籤一起出現**,不靠顏色單獨表意;
  和局不上色 —— 用 `--draw` 的橘色會讓「和局」看起來像警告。

上下半場的進失球本來就是一個 2×2,改用 `C.statMatrix()` 攤成矩陣 ——
「哪個半場進得多」一眼看得出來,壓成兩行斜線就要自己比對兩行的第一個數字。

## 不做的事(同樣重要)

- **單一進球的球員級「進球方式」** —— Understat 給的是球隊整季摘要,
  把某一類掛到某位球員的某一顆球是我們沒有的資料。球員逐球表不要加那一欄。
- **把沒通過驗收的特徵放進模型** —— 近五戰與交手紀錄的係數是 0,
  `npm test` 有一條專門守著。直覺上該有用不是理由。
- **大量爬網站** —— 靜態檔下載沒問題,官方進球事件是零額外請求。
  一場一個請求的做法先不要做。探測腳本自己也有請求硬上限。
- **為了畫面好看補測試資料** —— 要真實數字就在有 Secret 的 runner 上跑,
  不要寫假資料進正式快取。
- **拿賽後重建的模型冒充賽前預測** —— 沒有賽前快照的場次,`prediction` 就該是 `null`。
- **留一個永遠空白的欄位** —— 比不做更糟,讀者會以為是壞掉。
  拿不到就在畫面上說拿不到,並說明是「拿不到」還是「還沒到」。
- **賽前分析頁的「兩隊陣容對照」** —— 2026-08-27 移除。它跟同一頁上面的
  先發陣容球場圖講的是同一批人,只是換成依角色分帶並排;兩塊並存等於
  同一份資料畫兩次,改了一邊另一邊會悄悄過期(風格卡踩過同樣的坑)。
  要看站位看球場圖,要看角色看戰術頁的攻守分型。**不要加回來。**
- **觀點區的「新聞／名宿／專家」分類鈕** —— 2026-08-27 移除。每場總共約 3 筆,
  一顆鈕後面常常只有一筆,切換的成本比省下的翻閱多。改成合成一串直接翻,
  順序仍是新聞 → 名宿 → 專家(所以打開就是新聞),分類本身留在每張卡的標籤上。
  等到單場觀點筆數穩定在十筆以上再談分類。
