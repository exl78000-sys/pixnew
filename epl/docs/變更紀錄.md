## 2026-09-01：單場分析頁加「提到這兩隊的外電」

外電對到球隊之後，單場分析頁就接得上了。實測 AVL 0-1 ARS 那一場，
六則全是這場的實際賽報：Guardian 的即時文字轉播、BBC 與 Sky 的賽報、
球員評分 —— 新聞一直都在，只是沒有接上。

- **跟「新聞／名宿／專家觀點」分開成獨立區塊。** 那一區是人工核對過的具名觀點，
  它的價值就在嚴格；把機器比對出來的外電混進去會把那條線弄糊。
- 標題寫「**提到這兩隊的外電**」而不是「本場新聞」，並在卡片底部寫明
  **依球隊名自動比對、不保證是在講這一場**（轉會、傷停、教練里程碑的報導
  也會提到同樣的球隊）。
- 排序把「兩隊都提到 + 日期在開球前後兩天內」放最前面，並標「兩隊都提到」——
  那是**事實**（兩隊名字都出現），不是推論（所以是本場報導）。
- 外部連結一樣走 `safeUrl`；有譯文就顯示中文並標「機器翻譯」。
- 位置在「專家觀點」與「本站 AI／模型分析」之間。

## 2026-09-01：外電對到球隊（原本 RSS 完全沒有 team 欄位）

使用者回報「英超比賽新聞還沒抓取」。查證：RSS **有在抓、而且是新的**
（今天 45 則，BBC／Guardian／Sky 三個來源），但**50 則裡有 0 則帶 `team`**——
所以球隊頁、單場分析頁、動態頁的球隊篩選通通看不到它們。抓了卻沒接上，
畫面上就等於「沒有」。

- 新增 `lib/news-tag.mjs`（三聯賽共用）：從名冊的 `en` / `of` / `alias` 加上
  一小份媒體慣用簡稱（Spurs、Forest、Palace、Villa…）建詞組表，
  對 `title + body` 做**詞界**比對。
- **配錯隊比配不到糟**，所以三道防線：只用完整詞組（`Manchester` / `United` /
  `City` 這種多隊共有的泛詞一律不用）、**同一詞組對到兩支球隊就整個丟掉**、
  詞界比對（`Villa` 不會命中 `Villarreal`）。
- 一則新聞常講到兩隊（轉會新聞），所以輸出 `teams` 陣列；`team` 取**標題裡
  最先出現**的那一支。位置要取該隊**所有詞組裡最靠前**的 ——
  只看第一個命中的詞組會出錯：「Man City open talks with Chelsea」的標題是
  Man City，但先命中的是 body 裡的 Manchester City，MCI 因此被排到 Chelsea 後面。
- 前端球隊篩選改吃 `teams` 陣列 —— 只看 `team` 的話，用第二支球隊去篩會篩不到
  自己明明有提到的新聞。
- 結果：英超 40/45 則對到球隊（沒對到的 5 則確實是全聯賽性質，例如
  「Premier League team of the week」），24 則講到兩隊以上。
- 人工交付本來就標好 `team` 的那 80 則不覆蓋。

## 2026-09-01：外電譯文改走人工交付（不接 API 金鑰）

使用者決定：**為了安全不接 API**，改人工翻譯上架。這正好回到本站既有的
「收件匣 → 核對 → 發布」慣例（跟外電摘要、租借、教練職涯同一套）。

- `npm run news:todo`：產生**待翻清單 + 可直接複製的提示詞**。只列還沒有譯文的
  （依內容雜湊認得），第一次約 120 則，之後每天只有新增的十幾則。
  提示詞把界線寫死：只做語言轉換、數字照原文、人名隊名保留英文
  （本站其他地方也用英文隊名，音譯會對不起來）、翻不了就 `ok:false` **不要猜**。
- `npm run news:zh`：收件匣 `data/manual/news-zh.json` → 譯文快取（build 讀的那份）。
  **翻譯的正確性沒辦法自動驗**（那要另一個翻譯來對，等於換一個地方猜），
  所以只擋四種結構錯誤，而且退回的逐筆印出來：key 對不到現存外電（清單過期）、
  `ok:false` 或標題空、譯文跟原文一模一樣（沒翻）、標題裡沒有中文字。
  實測 5 則交付：1 收下、4 全部照預期退回。
- **譯者身分照實標**：交付檔的 `by` 是 `human` 就標「人工翻譯」，是模型名就標
  「機器翻譯」。把機器翻譯講成人工翻譯是說謊（鐵則四）；反過來只是保守。
  動態頁與單場分析頁兩處都跟著改。
- 流程寫在 `data/manual/README-news-zh.md`。
- API 那條路徑保留但不需要 —— 沒有金鑰時本來就安靜跳過。

## 2026-09-01：外電翻譯改成三個聯賽共用一條管線

查出兩個各自獨立的問題：

1. **英超根本沒有翻譯管線。** `translate-news.mjs` 的來源與快取路徑是寫死的
   `news-la-liga.json` / `news-la-liga-zh.json` —— 只做西甲。英超那 45 則外電
   從來沒有經過翻譯，動態頁上一直是英文標題，看起來像「翻譯壞了」，其實是沒接。
2. **翻譯從未實際執行。** CI 的 `ANTHROPIC_API_KEY` 是空的，每次都走
   「⚠ 沒有金鑰，略過翻譯」那條分支。西甲譯文快取因此是 0 筆。

處置：

- 新增 `lib/news-zh.mjs`：三個聯賽的外電/譯文檔名表（`NEWS_FILES`）、
  內容雜湊鍵（`newsKeyOf`）、掛載函式（`attachNewsZh`）。三支 build 共用，
  不各寫一份。
- `translate-news.mjs` 改吃 `--league=pl|es1|en2`，預設英超。
- `package.json` 三支指令；`epl-live.yml` 一次翻三個聯賽，回寫清單收三份譯文快取。
- 快取鍵維持「標題+摘要的雜湊」——RSS 的 id 是「來源+序號」，序號會隨新文章
  位移，明天的 0 號跟今天的 0 號是不同文章。
- 譯文一律**附在原文旁邊**、標「機器翻譯」，不取代原文（鐵則四，前端本來就對）。

**還缺一件事**：要真的有中文，得在 repo 的 Actions secrets 設 `ANTHROPIC_API_KEY`。
沒有它時整條管線安靜跳過、畫面顯示原文並標明 —— 這是設計，不是故障。

## 2026-09-01：安全稽核 + 不讓搜尋引擎收錄（個人使用）

安全稽核（實際掃描，不憑印象）結果與處置：

- **外部網址進 `href` 沒有驗 scheme**（唯一實質發現）。`esc()` 擋得住「跳出屬性」，
  擋不住 `javascript:alert(1)` —— 而這些網址來自 RSS（外部）與人工交付的收件匣，
  都不是我們能控制的字串。目前 738 個連結全是 https（沒有實際暴露），
  但那是靠上游自律。新增 `core.safeUrl()`：只放行 http/https，其餘回 null 讓
  呼叫端不要出連結；新聞連結、租借出處、Understat 來源三處都改走它。
- 掃過而**沒有**問題的：版控無憑證字串、無硬編金鑰、workflow 只在 `env:` 用
  機密不 echo、Worker 不印 token、`/status` 回應不含機密、`target=_blank`
  全部有 `rel=noopener`、發布產物無授權欄位。
- 已知殘留：`Exl78000@gmail.com` 曾隨 `.wrangler` 快取進入 git 歷史
  （已從工作樹移除並 gitignore，但歷史仍可查；要根除需改寫歷史）。

不讓人搜到（使用者要求：個人使用、隱密為主）：

- `web/robots.txt`：`Disallow: /`
- 16 個頁面 `<head>` 全部加 `<meta name="robots" content="noindex, nofollow">`
  （放在 `charset` 之後 —— 爬蟲可能只讀前面幾 KB），單檔版也標。
- 兩層都要：robots.txt 是「請不要爬」，noindex 是「就算爬到也不要收錄」。
- **倉庫本身仍是公開的**（轉私有會撞 Actions 分鐘數上限，見 08-31 的評估）。

## 2026-09-01：點火器 Worker 上線，並修掉它自己的沉默失效

Worker 部署後第一次 `/status` 正常（無比賽 → 什麼都不做），但那條路徑
**完全沒碰到 GitHub API**，於是暴露出兩個問題：

- **`isBusy()` 把「問不到」當成「忙」**。token 過期或權限被改時，每一次都
  「不重複派送」—— 看門狗永遠不動，而且沒有任何地方會講。那正是這支 Worker
  要消滅的故障形態，自己卻犯了。改成 `runState()` 三態
  （`busy` / `idle` / `unknown`）；該派送而狀態是 `unknown` 時**送告警**。
- **新增 `authHealth()`**：沒有比賽的日子碰不到 GitHub API，token 失效會潛伏到
  下一個比賽日才發作。改成每次執行都戳一個唯讀請求，`/status` 的 `auth` 欄位
  隨時看得出來（401 token 失效／403 權限不足／404 repo 或存取權不對）。
- **公開網址改唯讀**：workers.dev 的網址任何人都打得到，而 `/status` 會真的
  派送 workflow。現在沒帶 `?key=`（`STATUS_KEY`）時只報告不動作，判斷結果
  照樣整份回傳。cron 走 `scheduled()`，不經過這條路徑，永遠是執行模式。
- `preview_urls = false`，少一組公開網址。

## 2026-08-31：點火器 Worker + 比賽日迴圈「判斷不出來就收工」的修正

**起因**：規劃 Cloudflare Worker 時做的第一次乾跑（假 token、不會派送）就抓到
真的故障：AVL vs ARS 19:00 開球，19:10 時即時資料已 10 分鐘沒更新，而
`epl-matchday` 在 **19:00 整** 就「completed」結束了 —— 整場比賽零輪詢。

**根因**（不是 cron，也不是 `decideWindow`）：迴圈的收工判斷寫成
`if [ "$(… .active)" != "true" ]; then break`。那條管線只要有一點閃失
（輸出空、JSON 壞、`fixtures.json` 剛好被同一輪的 build 改寫到一半），
就會被當成「比賽都結束了」。拿當時的真實資料重跑 `decideWindow`，
它回的是 `active: true`。

- 兩支比賽日工作流程改為 **只有明確收到 `false` 才收工**；解不出來印 `unknown`
  並繼續跑。多跑一輪的成本，遠低於漏掉一場比賽。
- 新增 `infra/ignition-worker/`（Cloudflare Worker，進版控）：
  - **點火**：比賽快開打而沒有 job 在跑 → 派送比賽日迴圈。
  - **看門狗**：比賽正在踢而即時資料 > 6 分鐘沒更新 → 自動補派送；
    > 15 分鐘 → 送 webhook 告警。這是本站第一個會「主動說壞了」的機制。
  - **收工部署**：當天最後一場結束 30 分鐘後補一次完整建置與部署。
  - 無狀態（不用 KV，冪等靠「派送前先問 GitHub 有沒有 job 在跑」）；
    窗口故意比工作流程寬（95/155 對 75/140），因為它只是扳機，
    真正的判斷仍在 `live-window.mjs` —— **兩邊不是同一份邏輯，也不應該是**。
  - GitHub 原本的 cron 不拿掉，兩條路徑並存。
- 依據：實測前七天 `epl-matchday` 完全沒有 job 在跑的空窗中位數 43 分鐘
  （設定 15 分鐘）、只有 5% 在 20 分鐘內接上、最長一段 44 小時。
- 部署步驟見 `infra/ignition-worker/README.md`。**token 由使用者自己開**
  （fine-grained、只勾這個 repo 的 Actions: Read and write），本站不經手憑證。

## 2026-08-31：外電抓取修「先切再篩」，西甲來源補齊

- `parseFeed()` 原本 **先 `slice(0, max)` 再用關鍵字 filter**。對「綜合 feed +
  關鍵字」那種來源等於只拿最新 max 則去比對：西甲那筆 BBC 綜合足球有 80 則、
  其中 2 則與西甲有關，但程式只看前 8 則 → 每天穩定收到 0 則，且不會報錯。
  改成先篩再切（`max` 是「最多收幾則」，不是「只看前幾則」）。
- 西甲 `maxPerFeed` 8 → 20（Guardian 實測有 20 則可用，卻被砍到剩 8；
  英超 15、英冠 20，只有西甲設得特別低）。
- 新增來源 **Sky Sports 西甲（rss/11835）**：2026-08-31 實測 20 則，
  約 14 則明確提到西甲球隊，離題比例與英冠既有兩個來源同級。
- 退回 **ESPN `?league=esp.1`**：實測回的是全歐綜合（Chelsea、Messi 退國家隊、
  Benzema 離開 Al Hilal），那個參數沒有實際過濾 —— 跟 Sky News 綜合體育同一種坑：
  **來源的名字不等於它的內容**。已記進 `_rejected`。
- Marca 與 AS 實測內容正確且量大（47／68 則），但**是西班牙文**，而
  `news:translate` 目前產出 0 筆（沒有 ANTHROPIC_API_KEY 就安靜跳過）；
  加進去只會讓西甲動態頁變成一整頁西班牙文，所以記進 `_spanish_pending`，
  **等翻譯確實運作再開**。
- `fetch-news.mjs` 加上「只有直接執行才跑主流程」守衛並匯出 `parseFeed`，
  才測得到行為而不是掃原始碼（跟 `fetch-official.mjs` 同一個慣例）。
- 結果：西甲外電 12 → 54 則、RSS 來源 1 → 3 個。英超與英冠沒有關鍵字篩選，不受影響。

## 2026-08-31：實時頁「開賽倒數」移到最上面

- 版面順序改為：開賽倒數 → 進行中 → 剛結束 → 還沒有賽果 → 已完賽 → 積分榜。
- 理由：這一頁最常被用來回答「下一場什麼時候踢」，而倒數原本壓在三個區塊下面；

## 2026-08-31：進球認領改白名單（收口）

- `goalsOf()` 的認領資格由「排除已知非進球型別」改為「必須看得出是進球」：
  型別在 `G/O/P/OG` 或 description 在 `G/P/O` 才有資格認領比分變化。
- 原因：黑名單擋不掉沒見過的代碼。紅牌 `R` 不在黑名單、又帶 `personId`，
  真正的進球事件若剛好缺 `personId`（烏龍球有此形狀），同一比分下的紅牌會勝出，
  射手被安到吃牌的人身上 —— 而品質檢查抓不到，因為 `person` 不是 null 只是錯的人。
- 認不出是進球時保留 null，交由完賽品質檢查退避重抓（配錯人比配不到糟）。
- 新增兩條回歸測試：無射手烏龍球撞同比分紅牌、未知代碼不得認領。
- 實測目前 61 顆進球型別全為 `G/O/P`，白名單 100% 覆蓋，無回歸。

## 2026-09-01:專家觀點空的時候不要留一張大空卡

使用者看單場分析頁問「這樣這欄沒用了?」——畫面上是「0 筆已核對／本場尚無可驗證的
名宿・專家觀點」一張整卡,而它正下方就是有六則內容的「提到這兩隊的外電」。

查證:`expert-opinions.json` 有 30 則、涵蓋 **10 場**,而且全部是 2026-27 第 1 輪。
它是人工整理的,不會自己長 —— 所以第 2 輪之後每一場都是那張空卡。**那一欄不是沒用,
是覆蓋率低**,而低覆蓋率不該用一張大卡去宣告。

- 空的時候**整區(連標題)都不畫**,那句承諾折成外電卡的第一行:
  「0 筆已核對・本場沒有經人工核對的具名觀點……下面這些是機器依球隊名比對的外電,
  不是專家發言」。區別還在,而且就在讀者眼睛所在的位置。
- **兩區都空才留原本那張空卡** —— 否則讀者不會知道「人工核對觀點」這件事存在。
- 兩個呼叫點(賽後面板、綜合對比面板)合成一個 `opinionSections()`。兩處各寫一次
  的話,改了一邊另一邊會悄悄過期(CLAUDE.md 已經記過這個坑)。

**順帶記一個測試的假紅**:註解裡寫「一整季 380 場」會命中
「分析頁的『整季 N 場』不寫死 380」那條斷言 —— 那條守的是顯示字串,但它掃的是整份
原始碼,連註解都算。改寫措辭即可,不要為此放寬斷言。

**還沒做的**:這兩區都只掛在 `f.played` 的面板裡,**未賽的比賽兩區都不出現**。
賽前其實才是外電最有用的時候(轉會、傷停、教練談話)。這是既有行為,不是這次改動
造成的,列在補齊規劃。

## 2026-09-01:提前開踢的場次會把真正的下一輪擠掉(西甲沒有下一輪倒數)

使用者問「西甲為什麼沒有下一輪倒數」。查到的是規則的反向盲點:

西甲 2026-27 第 6 輪的 **RSO vs CEL 移到 9/3 開踢**(同輪其餘九場在 9/16)。
`countdownFixtures` 的規則是「開球順序上第一段連續同輪」,碰到它就停住 ——
畫面變成「**第 6 輪・1 場**」一張卡,而 9/5~9/7 的**第 4 輪十場**(含 9/5 的
Real Betis vs Real Madrid)全部掉進「下一批:第 4 輪…起」那一行小字。

原本的規則是為了另一個方向設計的:**延後**的補賽(2025-26 第 31 輪 MCI vs CRY
晚了 53 天)自成一段是對的。差別在跟後面那一段比大小:

- 輪次比後面**小** → 延後的孤兒,就此打住(既有行為,測試守著)
- 輪次比後面**大** → 它插到更早的一輪前面,**它不是下一輪**,要繼續往下收

不需要 magic number,也不需要知道一輪有幾場。標題改用**這批裡最小的輪次**
(真正的下一輪),不是第一場的輪次;提前的那幾場另外用一行講清楚它是哪一輪、
同輪其他場次在哪一天(那幾場多半還沒公布開球時間,所以要數 `fixtures` 不是
`upcoming`)。

修完:西甲「第 4 輪・11 場」,十一張卡;英超仍是「第 3 輪・10 場」不變。
`npm test` 加兩條(提前一場、連續提前兩場)。

## 2026-09-01:西甲賽後分頁改成使用者指定的順序

使用者指定:**比分 → 進球/事件 → 外電 → 本站分析 → 戰術 → 陣容 → 數據**,
並且「依照西甲現有欄位為主」。比分在頁首那張大卡(不在分頁裡),其餘依序排。

原本的問題是那七張賽後卡是**綁死一串**的(`matchReportCards` 回一整段 HTML),
所以「完整比賽事件」被埋在最後面、外電與本站分析插不進中間。

- `matchReportCards(m, { order })` 加了選單參數,七張卡各自具名:
  `tactics / lineups / compare / teamStats / players / events / best`。
  **不給 order 就是原本的順序**,英超那一頁逐節比對過,輸出沒變。
