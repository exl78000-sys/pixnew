## 2026-09-03:FotMob 英超逐場資料接進真實管線與 Obsidian vault

使用者指示:模擬遊玩抓的那批真實資料(控球、球隊統計、逐射門 xG、動能、事件、名單)要接進系統,
「另一方面也存進資料庫」—— 資料庫指的是 **Obsidian 本地 vault**(不是 SQL)。

### 接法

- `scripts/lib/matchstats.mjs`(真實管線):讀 `data/raw/fotmob-epl/`,**再核一次比分**(對本站賽果;raw 是人也能改的檔),
  控球相加要 100;shotmap 進球數 ≠ 比分的場次標 `shotmapComplete:false`。產 `web/data/matchstats.json`(400 場,4.2 MB;
  頁面不直接載它)、把逐隊彙總掛到 `teams.json` 的 `matchStats`(沒資料的隊不加鍵)、把本季場次轉成 canonical detail 掛到
  `reports.json` 的 `advanced`(順位在 SportMonks、API-Football 之後,但那兩家對英超本季都是 0 場)。
- 單場分析頁:既有的「完整球隊攻守數據」卡直接吃到控球(加上下半場)、射門、角球、犯規、撲救、傳球、xG;
  新增兩張卡 **比賽動能**(供應商逐分鐘指標,本站只搬運)與 **射門圖**(半場圖,圓大小 = xG、實心 = 進球)。
  沒有逐人評分的來源不畫球員評分卡,本場最佳退回 FPL 表現分 —— coverage 照實標,前端據此決定。
- 球隊頁:新區塊「逐場統計」(主客場均值:控球 ± 標準差、射門/被射門、xG/xGA、角球、犯規;射門情境份額與 xG/射門)。
  跟「上季數據風格」是不同來源(Understat 整季分類 + FPL),各標各的,數字不會完全一樣。
- **Obsidian vault**:比賽筆記多一節「逐場統計(FotMob)」(球隊統計表、逐射門表、事件、動能序列、抽核說明),
  球隊筆記多一節主客場彙總與射門情境。400 則比賽筆記都有。

### 控球率兩季都抽核了

抓取器的 `--verify` 原本只認本季(fixtureId 在 pulselive 快取裡);往季改成打官網賽季清單找到該季、拉整季賽程
(5 個請求)再抽核。2025-26 抽 20 場:**20/20 在 ±1 內**(最大差 0.5)。兩季的抽核結果都寫在 `matchstats.json`
的 `verification`,畫面與筆記照它講。

### 踩到的

`attachAdvancedCodes` 的來源標籤寫成「不是 SportMonks 就是 API-Football」—— FotMob 接進來後,單場分析頁的卡片
標成 API-Football,而測試一條紅才發現。改成照抄 detail 的來源。這是「二元式在第三個來源出現時靜靜出錯」的又一例
(`league()` 那條坑的同型)。

| 側寫 | `scripts/game/lib/profile.mjs` + `scripts/game/build-game.mjs`(`npm run game:build`,已掛進 `npm run build`)→ `web/data/game/pl.json` |
| 校準 | `scripts/game/calibrate-xi.mjs` → `data/game-calibration.json`;先發濃縮檔 `data/raw/fpl/2025-26-xi.json` |
| 引擎 | `web/assets/js/game-engine.js`(純函式,node 測得動) |
| 版面 | `web/assets/js/game-view.js`(探索頁的「模擬遊玩」分頁,view 鍵仍是 `duel`,舊書籤不斷);`duel-view.js` 移除 |
| 測試 | `scripts/game/test-game.mjs` + `scripts/game/lib/engine-checks.mjs`,掛進 `npm test` |

前端模組**不用子目錄**,用 `game-` 前綴放在同一層 —— bundle 的 SHARED 與 stamp-assets 的規則
都只認同一層的 `./x.js`,開子目錄要改兩套機制,前綴就夠了。
隔離由測試守四條:真實管線沒有檔案 import `game-*` / `scripts/game/`(宿主 `page-explore.js` 除外,
它只 import render)、`build-game` 只寫 `web/data/game/`、`profile.mjs` 沒有 writeFile、
**沒有任何改動時引擎的 λ 精確等於站上的 λ**。

### 控球率:兩個來源都探到了,主 FotMob、官網核對

`probe-possession.mjs`(3 個請求)實測:FotMob `matchDetails` 的 `content.stats.Periods.{All,FirstHalf,SecondHalf}`
有 `BallPossesion`(上游拼字);官網後端 `/stats/match/{fixtureId}` 的 `data[teamId].M` 有
`possession_percentage`(160 多個統計項裡的一個)。FotMob 的聯賽賽程端點一次回整季 380 場的 matchId。

抓取器存**精簡萃取**(一場 20 KB,不是原始 200 KB):球隊統計、上下半場控球、事件、逐射門
(xG / 情境 / 座標 / 結果)、逐分鐘動能、名單與替補席。2025-26 全季 380 場 + 2026-27 20 場,
比分全部對得上本站賽果、shotmap 進球數全部等於比分。官網核對 20 場控球:**全部在 0.6 個百分點內**。

順手發現 FotMob 的球隊統計裡有 `physical_metrics_distance_covered` / `sprinting`、逐人有
`totalDistanceCovered` / `topSpeed` —— 本站一直寫「跑動資料沒有免費來源」,**這一條要重新探**,
記進補齊規劃。這次沒有收進萃取(萃取規則改了要 +1 版本重抓)。

### 校準:a = 0.75 ± 0.47,跟 0 分不開

用 2024-25 的 xGI/90 算 2025-26 每場先發的 Q,前半季調、後半季驗:點估計 0.75、標準誤 0.47,
後半季概似增益 +1.23(a=1 時 +0.96)。**效果方向對、量沒驗證出來**,照規劃標成遊戲規則,畫面寫明。
防守側 2024-25 快照沒有逐人防守 per-90,校不了,借用同值。

先發樣本得從 FPL 鏡像的 `merged_gw.csv`(靜態檔,5 MB,不進版控)濃縮 ——
本站的逐場進球明細只有進球與助攻的人,不是完整先發。濃縮後 760 隊-場,2 場先發不是 11 人的排除。

### 引擎踩到的

- **比分不能事先抽好**(規劃就寫了):改成逐分鐘 Poisson,分鐘權重用 1,107 顆真實進球的分布,
  下半場佔 61%。沒有 Dixon-Coles 修正,畫面上寫明;300 場平均進球在 λ 的 3 個標準誤內。
- **同一分鐘兩次換人會把剛上場的人又換下**:第二次從「現在的場上」挑,規則上合法,實測 300 場裡有。
  排除 `cameOn` 的人。
- **Q 不能連紅牌一起扣**:少一人的效果由 RED 常數給(跟 `inPlaySim` 同組 0.72/1.30),Q 再少一個人就重複算。
- 檢查器第一版拿「分鐘開始前」的名單驗事件,同一分鐘先換人再犯規時新上場的人拿牌被判成不在場上 ——
  檢查器要依序套用同一分鐘的事件,不是引擎錯。
- 把先發裡 xGI 最高的換成替補裡最低的,**客隊的 λ 也會動** —— 換掉的人防守能力也不同,那是設計。測試預期改了。

### 動畫

`duel-anim.js` 加 `perform(e)`:換人改名(帶背號)、紅牌退場(`active()` 之後所有迴圈都不看他)、
黃牌閃圈、射門不進演一段推進再射偏 / 被撲 / 被封 / 中柱(`shootMiss`)、角球把球擺到角旗、主罰者持球。
控球份額改吃引擎抽的目標(`possHome`),沒給才退回 λ。既有的無畫布測試台全部照過。

### 單檔版兩個既有的坑(做這一頁時撞到的)

- **共用模組的具名 import 沒被拆**:bundle 只拆 `import * as C`,`import { blendPair } from './predict-core.js'`
  留著 → 攤平後跟 predict-core 的函式撞名,一開單檔版就 `Identifier 'blendPair' has already been declared`。
  舊的 duel-view 有一模一樣的 import,所以對戰模擬併進探索頁之後單檔版那一頁其實一直是壞的 ——
  分頁版正常、測試全綠、沒有人用單檔版開那一頁。現在共用模組也拆具名 import,並加一道守門:
  攤平之後還有 import 行就直接打包失敗。
- **探索頁的 import 寫 `?v=0`,資產戳從來沒打上去**:`stamp-assets` 的正則只認 8 位十六進位的戳,
  `?v=0` 既不會被 strip、也對不上 `'./x.js'` 的替換 —— 三個 view 模組(足球知識 / 模擬遊玩 / 球員搜尋)
  在 GitHub Pages 上都吃不到新版戳。改回不帶後綴,讓 stamp 自己打。CLAUDE.md 那條「import 一律用正則」
  講的就是這個,我寫版面時照抄了舊檔的寫法。
- **沒有 `<meta charset="utf-8">`**:用 `python3 -m http.server` 開 dist 時整頁中文是亂碼(伺服器不帶 charset)。
  補上。`.claude/launch.json` 加了 `warroom-dist`(port 5174)專門看單檔版。

### 沒做、要做

- 動畫的**位置層避讓**(球員仍會穿過)、精華模式現在只是「連跳沒事件的分鐘」。
- 跑動 / 衝刺資料:FotMob 有,要重探並改寫 CLAUDE.md 那條「沒有免費來源」。
- 替補球員的能力 null 佔比:先發 220 人裡 33 人兩季都不到 450 分鐘(新援居多),用角色中位數。

規劃寫在 `補齊規劃.md` 的「對戰模擬重製」一節,重點三件:

- **目標是 FM24 的 2D classic 畫面加周邊面板**,不是 3D。不引入遊戲引擎、
  「示意比擬真誠實」這兩條既有決定都不推翻。
- **把「發生什麼」跟「怎麼演」拆開**:build 產每隊事件側寫(`duel-profiles.json`)、
  瀏覽器端純函式事件引擎(`duel-engine.js`)產整場事件流、動畫只負責照劇本演。
  比分與射手隊伍仍來自 `sampleMatch`,同種子同比分不變。
- **每個要素都先指到一份真資料才算數**。逐檔實測過的:換人次數 / 分鐘 / 被換下位置
  (`official.json` 20 場 182 次)、射門 / 角球 / 犯規 / 牌(football-data 逐場 CSV)、
  進球情境與各情境 xG/射門(Understat)、上下半場進球 44.9% / 55.1%(9 季 7,682 球)、
  逐球分鐘(小樣本,英超 30、西甲 45,畫面要標 n)。控球率英超**沒有來源**,列成決策。

順便抓到現況一個不一致:射手從**全隊**進球佔比抽,先發是按分鐘取前 11,
兩份名單不同批,畫面上可能出現不在場上的人進球。重製的階段 1 會修。

### 同日拍板:獨立管線、換人改機率、黃紅牌、只做英超、控球率要抓

使用者的四項決定(原文收在規劃裡)改寫了規劃的骨架:

- **模擬遊玩是獨立管線**:`scripts/game/` 與 `web/assets/js/game/`、產物 `web/data/game/`,

- **控球率**:英超目前沒有,先寫探測(FotMob `matchDetails` vs pulselive `/stats/match`),

## 2026-09-02：跑位動畫加入幾何避讓

使用者要的是「路線繞過去」而不是把球員互相推開。`duel-anim.js` 新增
`avoidanceOf()`：球員進入彼此的近距離且正在接近時，沿兩人連線的切線偏移
動畫目標；同一對球員採同一個世界方向的切線，避免兩人各自閃向相反方向。

- 避讓只改繪製前的動畫目標，不讀比分、模型機率或進球排程。
- 所有計算仍是零依賴、可由同一個種子重現；邊界限制與既有的進球保底不變。
- `scripts/test.mjs` 增加切線方向的直接測試，並在四個種子跑完整場時檢查球員最小間距。

### 2026-09-02 覆查:三處修正

實際跑過之後改了三件事,原本的敘述有兩處講太滿。

**1「不會改變模擬結果」太強,已改成「不改變比分與進球排程」。**
實測 seed 1 的控球率 54.8% → 46.5%(另外三個種子完全相同)。原因不是避讓讀了
比分,而是:避讓改位置 → `toGoal` 變 → 快攻射門早一拍或晚一拍 → `chooseNext()`
少呼叫一次 → **rng 流錯位**,之後整條路徑就不同了。比分不受影響(模型排的,
24 個種子都演出 2 顆),但避讓不是完全惰性的,下一個人要知道。

**2「跑完整場時檢查球員最小間距」證明不了那句話。** `__animProbe()` 是呼叫當下
的快照,而測試跑完才叫一次 —— 它看的是**最後一格**。逐格量下來:全場最小間距
中位數 **0.11 m**(24 個種子,最大 0.26 m),5~9% 的畫格有球員疊在一起。
也就是說球員還是會穿過去,只是比以前少(壅擠畫格 24 個種子:無避讓
7.6~22.7%、有避讓 5.1~12.9%)。

**兩個分佈重疊,單一門檻分不開**,所以防線改放在**純函式**上(精確值、無門檻):
偏移垂直於連線、迎面兩人偏同一個世界方向、太遠不閃、背對著走不閃。
跑完整場那條降級成毛胚(壅擠畫格 < 20%),註解裡寫明它守得到什麼、守不到什麼。

**3 找到一條會隨時間飄的假紅。** `node scripts/test.mjs` 單獨跑全綠、`npm test`
會紅同一條。原因:`last = performance.now()` 是 mount 當下的牆上時間,而無畫布的
測試台自己從 `now = 0` 開始餵時戳 → **第一格的 `dt` 是負的**,位置往目標的反方向
跳一下,跳多遠取決於行程已經跑多久(實測等 0/200/800 ms → 最小間距
0.20/0.008/0.13,差 25 倍)。瀏覽器不會給比 mount 更早的 rAF 時戳,所以只在測試台
發作。兩邊都修:模組把 `dt` 夾在 `>= 0`(負的 frame delta 本來就沒有意義),
測試台的合成時鐘從 `performance.now()` 起算。修完同種子跑三種起步時間,
結果一致到小數第四位。

**還沒做的**:避讓只改「目標點」,而積分每格只走 k≈0.1,兩人目標交叉時仍會穿過去
—— 所以壅擠只降了一半。要真的不重疊得在**位置層**再兜一次底(積分之後推開),
繞行決定路線、間距修正兜底,兩者不衝突。列在補齊規劃。

## 2026-09-01：點火器 Worker 上線，並修掉它自己的沉默失效

  照樣整份回傳。cron 走 `scheduled()`，不經過這條路徑，永遠是執行模式。
- `preview_urls = false`，少一組公開網址。

## 2026-08-31：點火器 Worker + 比賽日迴圈「判斷不出來就收工」的修正

**起因**：規劃 Cloudflare Worker 時做的第一次乾跑（假 token、不會派送）就抓到
真的故障：AVL vs ARS 19:00 開球，19:10 時即時資料已 10 分鐘沒更新，而
`epl-matchday` 在 **19:00 整** 就「completed」結束了 —— 整場比賽零輪詢。

**根因**（不是 cron，也不是 `decideWindow`）：迴圈的收工判斷寫成
`if [ "$(… .active)" != "true" ]; then break`。那條管線只要有一點閃失
（輸出空、JSON 壞、`fixtures.json` 剛好被同一輪的 build 改寫到一半），
就會被當成「比賽都結束了」。拿當時的真實資料重跑 `decideWindow`，
它回的是 `active: true`。

- 兩支比賽日工作流程改為 **只有明確收到 `false` 才收工**；解不出來印 `unknown`
  並繼續跑。多跑一輪的成本，遠低於漏掉一場比賽。
- 新增 `infra/ignition-worker/`（Cloudflare Worker，進版控）：
  - **點火**：比賽快開打而沒有 job 在跑 → 派送比賽日迴圈。
  - **看門狗**：比賽正在踢而即時資料 > 6 分鐘沒更新 → 自動補派送；
    > 15 分鐘 → 送 webhook 告警。這是本站第一個會「主動說壞了」的機制。
  - **收工部署**：當天最後一場結束 30 分鐘後補一次完整建置與部署。
  - 無狀態（不用 KV，冪等靠「派送前先問 GitHub 有沒有 job 在跑」）；
    窗口故意比工作流程寬（95/155 對 75/140），因為它只是扳機，
    真正的判斷仍在 `live-window.mjs` —— **兩邊不是同一份邏輯，也不應該是**。
  - GitHub 原本的 cron 不拿掉，兩條路徑並存。
- 依據：實測前七天 `epl-matchday` 完全沒有 job 在跑的空窗中位數 43 分鐘
  （設定 15 分鐘）、只有 5% 在 20 分鐘內接上、最長一段 44 小時。
- 部署步驟見 `infra/ignition-worker/README.md`。**token 由使用者自己開**
  （fine-grained、只勾這個 repo 的 Actions: Read and write），本站不經手憑證。

## 2026-09-01:已完賽場次的「賽前機率」原本是事後算的(英超)

規劃盤點時查到的,比原本排在前面的事都重要。

`build.mjs` 的模型擬合在 `[...history, ...curPlayed]` —— **含本季已完賽的比賽**;
接著把那組機率掛到**每一場** fixture,包括已賽的。走查回測的逐場預測
(`backtest-matches.json`)只涵蓋跑完的賽季,**本季 0 場**,所以本季已賽場次
拿到的就是全資料模型的輸出。

而單場分析頁把它標成「**01・賽前模型**」,還據此下兩個結論:
「模型賽前最看好的就是這個結果」、「模型 vs 市場誰給實際結果的機率較高」。
Elo 是逐場更新的 —— 那場的比分直接進了參數。**不是編數字,是把數字標錯,
而結論是從錯的標籤長出來的。**

**西甲與英冠的 build 從第一版就拒絕這樣做**(`prediction: m.played ? null : ...`),
所以那兩個聯賽是對的,要修的是英超。

### 修法

`prob-history` 的每場**第一個點就是開賽前凍結的機率**(第 0 分,`m.preMatch`,
完賽後封存不再改)。抽出共用的 `preMatchSnapshots(store)`(三個聯賽同一份),
然後把欄位拆成兩個:

- `prediction` —— **只放真正的賽前機率**:未賽 = 目前模型;已賽 = 開賽前快照;
  拿不到就是 `null`。
- `postFit` —— 已賽場次「目前模型怎麼看」。是背景資訊,畫面上標明它不是賽前預測。

覆蓋率:英超 10/20、西甲 7/30(從 0),每個比賽日增加。**補不回過去的場次** ——
快照要開賽前抓得到即時樣本才有,本站這一季才開始存。

### 畫面

- 沒有快照時,「實際結果的賽前信心」與「三向機率並排」**整個不畫**,並說明
  為什麼:那兩張卡整張都是拿賽前機率做的推論。
- 賽前分頁對已完賽場次加一句話,並把小標改成「目前模型・非賽前預測」;
  有快照的話同一句話裡把真正的賽前機率寫出來。
- 快照只有 1X2(它是曲線的第 0 分點),沒有賽前 xG —— 那兩列顯示「—」,
  四個 xG 全空時整張卡不畫。
- **西甲的綜合對比因此活了**:改用跟英超同一個 `phaseComparison`,
  有快照就有完整比較(實測 RSO|ESP:賽前 46/25/28、市場 50/26/24、賽後 2:1)。

`npm test` 加八條(含「已賽場次的 prediction 一定是快照」「postFit 只出現在
已賽場次」「沒有快照時那兩張卡不畫」「兩個聯賽走同一個 phaseComparison」),
`test-laliga.mjs` 那條舊斷言跟著放寬成「null 或快照」並補一條「快照不含 xG」。

## 2026-09-02:新增「我的預測」——自己猜,賽季末跟模型與市場比

4. **比較一律在同一批場次上做。** 市場盤口不是每場都抓得到,所以總表分兩組:

## 2026-09-02:我的預測加開賽倒數與自動上鎖

使用者要求「倒數開始」。兩層:

- **這一輪的抬頭**:下一場截止還有多久(是哪一場)、還有幾場可以填、幾場還沒填。
  用「還沒開賽的場次裡**最早**的那一場」,不是「第一場」—— 這一輪可能已經踢掉幾場。
  全部開踢就整行不畫,不要留一個永遠 00:00:00 的倒數。
- **每一場**:截止倒數(= 開球時間)。走 `C.countdown` / `C.startCountdowns`,
  跟實時頁同一份,不另寫一個計時器。

### 上鎖是就地改那一張卡,不是整頁重畫

掃描每秒都在跑,而**重畫會把其他場次還沒按儲存的輸入洗掉**。所以越過開球時間時
只動那一張:停用輸入、拿掉儲存鈕、把「截止 …」換成「已開賽・鎖定」。
實測驗過:第 4 張鎖住的同時,第 1 張正在打的比分與理由原封不動、還能繼續編輯。

### 一個自己差點種下的坑

`render()` 每次切分頁、換聯賽、按儲存都會跑一次,而 `C.pageInterval` **不會**
收掉上一個(`startCountdowns` 自己會收,它不會)—— 不處理的話來回切幾次就變成
十幾個掃描同時跑。現在每次重畫先 `clearInterval` 舊的。

`npm test` 加四條,含「上鎖不得走整頁重畫」與「計時器要先收掉」。

### 對著真實快取驗證,又抓到一個「0 看起來很像答案」

拿快取裡的 FotMob detail 實際產一份報告,跟同一場的 SportMonks 版逐欄位對照
(ALA 3-0 GET):陣型、先發 11、替補 5、進球 3、黃牌 4、射手三人、戰術解讀 3 條
**全部一致**,而且 FotMob **多了 xG 1.93**(SportMonks 那邊是 null)。

只有一欄對不上:**球場排數 FotMob 1 排、SportMonks 4 排**。

根因:我把 `xi[].grid` 留成 `null`,而 `rowsOf` 的實作是
`String(player.grid ?? '').split(':').map(Number)` —— **`Number('') === 0`**,
於是 11 個人全部落進「第 0 排」,球場圖會畫成一條線,**而且不會有任何地方報錯**。
這是本站記過的「0 是一個看起來很像答案的數字」的第三次。

兩層都修:

- adapter 依 `verticalLayout` 算出真正的 `grid`(「排:位」,跟 SportMonks 同格式)。
- `rowsOf` 硬化:空字串與 null 一律當成沒有站位資料,整份回 null 讓呼叫端退回 ——
  這是共用程式,任何供應商漏給 grid 都不該變成一條線。

### 逐人統計:四個欄位原本是空的

同樣對著真實資料修:`offsides` → `Offsides`(大寫)、對抗是 `duel_won` / `duel_lost`
兩個 key 要自己加、**逐人沒有「總射門」**這個欄位(只有射正/射偏/被封阻三個,
三個都在才相加,缺一個就留空 —— 湊不齊的和是錯的數,不是估計值)。

快取存的是**轉換後**的 detail(原始 payload 一場約 200 KB,整季會到七十幾 MB),
所以對映表改了之後舊快取不會跟著變 —— 加了 `--force` 重抓。

### 對映表版本:讓「要重抓」變成機制而不是「要記得」

快取存的是轉換後的 detail,所以每次修好欄位對映,舊快取都不會跟著變。
第一版的處理是加一個 `--force` 旗標 —— 但那要人記得,而記得不是機制。

改成 adapter 匯出 `ADAPTER_VERSION`,每筆快取記下產生它的版本;抓取器把
版本不同的場次自動列入待抓,並在 log 講明「其中 N 場是對映表改版要重抓的」。
受每次請求上限節制,不會一次全打。**改了欄位對映就把版本 +1**,寫在常數旁邊。

### FotMob 轉換的回歸測試(17 條)

用**合成 payload** 測,不依賴快取狀態 —— 欄位形狀是探測出來的真東西,
測試守的是轉換不要走樣。這一層會出的錯**都不會拋例外**:欄位名猜錯 → 那一欄
靜靜是 null;grid 給 null → 十一個人被畫成一條線;烏龍球掛到踢進的人身上 →
配錯人。掃原始碼掃不出這些,所以要真的轉一遍再看結果。

守的東西:實測過的 key(`Offsides` 大寫、`keeper_saves`、`shot_blocks`)、
沒見過的 key 要回報不要吞、分隔列不算數據、逐人總射門是三個相加、
對抗是 won+lost、Tackles 的 i18n key、牌從事件補、**烏龍球算給對面而且不掛射手**、
半場與文字評論不進時間軸、**先發要有真正的 grid**(4 排不是 1 排)、
轉出來的 detail 過得了賽後報告守門、比分對不上不發布、位置代碼是單字母。

**版本數字只回報不當紅線**:舊快取是加 `adapterVersion` 之前寫的,抓取器會自己
重抓,紅在這裡只會變成沒有人看的紅(`docs:check` 那條「會漂移的只回報、
人為改動才擋」的同一個分界)。當紅線的是**機制** —— 抓取器必須真的比對版本。

## 2026-09-03:足球知識 / 對戰模擬 / 球員搜尋併成「探索」單頁
