## 2026-09-11:通知鏈的自我測試;以及「把目標達成寫成 CI 紅線」

### 一、通知鏈加了一支自我測試

`notify-ci.yml` 的「沒失敗 → 不開 Issue」每次部署成功都在驗,但
**「失敗 → 開 Issue」與「恢復 → 關掉」這兩條從來沒有人驗過** —— 而它們正是
這整套東西存在的理由。要驗就得讓 CI 真的紅一次,而那不可以拿真實管線去做
(會擋部署、站上停更),所以獨立成 `notify-selftest.yml`:只給手動觸發,
`outcome` 選 `fail` 或 `success`,不碰資料、不 build、不部署,唯一副作用是那張 Issue。

它同時是**給未來的人的體檢工具**:GitHub 的通知設定、Watch 狀態、token 權限
都會隨時間失效,而失效的症狀是「什麼都沒發生」—— 靜靜的,跟這個專案一路
踩過的其他坑同一種。

### 二、涵蓋補到 36/36 的那一刻,測試紅了

昨天(9/10)寫進模型頁的那句「Fenerbahçe 與 Sabah FK 踢完第一場就會有評分」,
**一個晚上就成真了** —— 歐冠第 1 輪打完,bridge 模式下它們的評分長出來,
涵蓋從 34/36 變成 **36/36**、預測從 116 場變成 126 場。

然後 `npm test` 紅了,因為那條斷言寫的是:

```js
ok(m.coverage.ratedTeams < m.coverage.totalTeams, '有球隊沒有評分,而且照實記著')
```

**「一定要有球隊沒評分」** —— 把「目標達成」寫成了紅線。這跟 CLAUDE.md 那條
「把會隨資料變動的數字當 CI 紅線」是同一個錯。更難堪的是:**它下面那一段註解
本來就在警告這件事**(「不是『一定要有沒評分的球隊』—— 全部都有評分是好事,
那條會在補齊時紅」),寫註解的時候看著上一行卻沒改它。

改成守**計數自己不矛盾**(評分數不可能超過球隊數),涵蓋率本身印成 `·` 一行
只回報不擋。

**這一條值得記的不是 bug 本身,是它怎麼被發現的:** 不是有人去讀程式,
是**現實在一天之內把預測兌現了**,而斷言擋在那裡。寫「等某某條件補齊」的
斷言時,一律先問:**補齊的那一天,這條會變成什麼?**

## 2026-09-10:模型頁補上歐冠那個模型;CI 失敗通知抽成一份給四支 workflow

兩件都是「東西已經在跑,但沒有人看得到」。

### 一、站上有兩個模型,而模型頁只講了一個

歐冠頁掛著 116 場預測,而**模型驗證頁提到歐冠 0 次** —— 讀者在唯一該講出處的
那一頁一個字都查不到。更糟的是最後一段還寫死著

> 盃賽與洲際賽事需要不同的模型(加時賽、PK、兩回合、跨聯賽比較),本站目前只做聯賽。

那句在階段 C(跨聯賽 Elo)上線之後就是**假的**,而它在站上待了一天。
「每個數字都查得到出處」是這個站唯一的賣點,這個缺口比少一個功能嚴重。

補上的一節講四件事,**數字全部從產物讀,前端一個都沒有寫死**:

| | 內容 |
|---|---|
| 方法 | 為什麼不能直接比(各聯賽的 Elo 是封閉池)、單一評分池、歐冠場次當橋、沒有新模型也沒有新參數 |
| 驗收 | RPS 與基準線、改善 ± 標準誤與倍數、逐季拆開(整體贏了可能只靠一季) |
| 涵蓋 | 本季幾場兩隊都有評分、幾場有預測、沒有評分的是誰 |
| 界線 | 不預測加時與 PK、沒有為歐冠調主場優勢、能回測的偏向大聯賽對戰 |

加上兩張「量過而沒有通過」的表:三次「要不要收那十六個聯賽的域內賽果」的量測
(0.0149 → 0.0265 → **0.0063 ± 0.0033 沒通過**),以及逐聯賽 Elo 補正與機率銳化。

**為了不寫死,產物多了三個欄位。** 前端自己抄一份的話,改了 `lib/ucl-elo.mjs`
那邊會悄悄過期而畫面完全正常 —— 姓名配對那條坑就是這樣來的:

- `pool.leagues[].results` —— 這個聯賽的域內賽果有沒有進池子。
  **不要讓前端從 `played === 0` 反推**:模式一換(例如改收 N 季)推法就靜靜過期。
- `coverage.unrated[].reason` —— 沒有評分有兩種,意義完全不同而前端分不出來:
  `unmapped` 是對照表接不上(**本站的 bug**,要去修對照表)、
  `no-bridge` 是接得上但還沒踢過歐冠(**等比賽就好**)。
  講錯就是誤導讀者。目前 Fenerbahçe 與 Sabah FK 兩隊都是 `no-bridge`
  ——`idOf` 對得上、只是 2023-24 以來一場歐冠都還沒踢過。
- `rejected` / `poolTrials` —— 那些量測是**紀錄**(當時量的值),不是每次 build 重算,
  所以寫成 `lib/ucl-elo.mjs` 的常數再進產物,模型頁讀同一份。

歐冠的勝率區塊也加了一行連到模型驗證頁。

**踩到一個自己設的陷阱:** 新加的測試「模型頁不再寫『本站目前只做聯賽』」第一版
掃的是原始碼,而**我自己的註解裡就在講那句話** → 永遠紅,而紅的原因跟它想守的事
一點關係都沒有。先剝註解再掃 —— 跟 `**強調**` 那條掃描器同一個處理。

### 二、四支排程 workflow 失敗時一聲都不吭

`epl-live.yml` 有 notify job(失敗開 Issue、成功關掉),而
`epl-matchday` / `laliga-matchday` / `laliga-news-daily` **一個都沒有** ——
它們全是無人看顧的排程,紅了沒有任何人會知道。

抽成 `.github/workflows/notify-ci.yml`(`workflow_call`),四支都呼叫它。
**連 `epl-live.yml` 自己也改成呼叫** —— 留一份舊的複本就是等它跟新的分岔,
而分岔的症狀是「有一支的通知行為跟別人不一樣」,沒有人會發現。

三個設計決定:

1. **標籤帶呼叫端的識別字**(`ci-failure` + `ci:<key>`)。共用一個 `ci-failure`
   的話會**互相關掉對方的 Issue**:比賽日那支還紅著,外電那支跑成功就把它關了。
2. **判定只看呼叫端傳進來的 `toJSON(needs)`**,那是 GitHub 自己算的 job 結論。
   「是哪一步紅的」才去讀這次執行的 jobs(可重用 workflow 跟呼叫端共用 run id)。
   讀 jobs 那一段包在 `try` 裡:它只是講得更清楚的加分項,
   **讓它把整個通知一起帶走的話,CI 紅了反而更沒有人知道**。
3. **`probe-apis.yml` 刻意不掛。** 那是手動的探測,失敗本來就是它要回答的問題,
   而人就在旁邊看 log。替它開 Issue 只會製造雜訊,而「紅久了就沒有人看」
   比不檢查更糟(`docs:check` 那一列學到的)。

**踩到第二個(而且這個更兇):** 可重用 workflow 的 `inputs` 描述裡寫了
`description: '…(填 ${{ toJSON(needs) }})…'` 當說明 —— GitHub 把它當成**要求值的
運算式**,而 `needs` 在 `workflow_call` 的 inputs 這一層根本不存在,於是**整份
workflow parse 失敗**。症狀不是「通知壞掉」而是**四支 workflow 全部跑不起來**:
手動觸發直接被拒,排程也不會開火。發現它的唯一方法是**真的去按一次觸發** ——
本機 YAML 語法檢查全過、`npm test` 全綠,因為那是 GitHub 自己的運算式層在擋。

`npm test` 加了三條:邏輯只有一份、四支都接上、
**而且 `needs` 要涵蓋自己的每一個 job**(漏掉一個的話那個 job 紅了不會有人知道,
而 Actions 頁看起來一切正常)。第三條第一版把 `on:` 底下的 `workflow_dispatch:`
`schedule:` 也當成 job(縮排一模一樣)→ 永遠紅,改成只掃 `jobs:` 底下。
第一條也順手釘住「description 裡不准出現運算式語法」(拿掉修正、跑一次確認它真的會紅)。

### 還沒做的

`probe-apis.yml` 的通知(上面說明了為什麼不做)。使用者端還缺兩個勾選:
GitHub Settings → Notifications → Actions 選「only failed」、
repo Watch → Custom → 勾 Issues。**沒有那兩個勾,Issue 開了等於沒開** ——
9/8 那次 #1 就是這樣躺著沒有人收到。

## 2026-09-10:掃一遍「上游時差被寫成 CI 紅線」的同類問題

今天一天修了兩條同型的 bug(收盤價那條之後的第二、三次),所以主動掃了一輪。
掃法是**看每一條跨來源斷言比的兩邊是不是同一批東西**,而不是等它紅。掃出兩件:

### 一、依設計拒收之後什麼都沒留下

補比分(football-data.co.uk 與 FotMob)的規矩是「一場對不上就整份不採用」——
那是對的。但**拒收之後產物裡沒有任何紀錄**,於是兩邊都出問題:

- 讀者看到已經踢完的比賽還寫著「未賽」,畫面上沒有任何說明(鐵則四)
- 測試分不出「依設計拒收」與「補比分壞了」,於是
  `FotMob 已完賽的場次本站沒有一場還是未賽` 會紅

連鎖起來是:**一場上游爭議 → 21 場暫定賽果全撤 → 部署被擋 → 整站凍結**。

修法跟 `closingPending` 一樣:拒收寫進 `meta.model.scoreCheck.refused`,
畫面講得出來,測試也分得出兩種情況 —— 有拒收就只回報,沒拒收才是紅線。

(目前三個聯賽的 `refused` 都是空的,而英冠有 21 場靠 FotMob 暫定補上 ——
機制是通的,修的是「它哪天拒收時會發生什麼」。)

### 二、同一份資料兩個渲染路徑,一個 esc 一個不 esc

`model.caveats` 被首頁與模型頁各畫一次:首頁**直接插入**、模型頁走 `esc()`。
所以寫 `<b>` 會一頁粗體、另一頁印出 `<b>`。而實際上**兩頁都在印星號** ——
英冠的 `intro`、`boundaries[5]`、`caveats` 裡各有一句 `**強調**`,
而前端沒有 Markdown 處理器。

這是「註解裡的 Markdown 掉進 HTML 字串」那條坑**在資料裡的版本**,
所以 9/9 加的那條掃原始碼的測試看不到它。

契約定成**純文字**、兩個渲染路徑都 esc()。`npm test` 改成掃**整份 meta** ——
第一版只掃 `caveats`,漏了 `intro` 與 `boundaries`,而星號就在那兩個欄位裡。
最後用瀏覽器把十頁全開一遍確認:零命中。

## 2026-09-09:比賽夜之後倉庫裡的資產戳會不見(es1 / en2),`npm test` 在那段時間必紅

**怎麼發現的**:例行檢查,在 9/8 聯賽盃之夜之後的預設分支 checkout 上跑 `npm test` ——

## 2026-09-03:球的物理層、球員頁的跑動與熱區、賽前先發圖可點

### 球不再黏在腳下(使用者要求)

`duel-anim.js` 的球從「腳下或直線飛向目標」改成獨立物體:有速度、有摩擦(地面 5.5、空中 1.2 m/s²)。

- 出邊線的傳球條件看的是**球**離邊線多近,不是目標點:固定速度從場中央踢滾 15 m 就停了(實測整場 0 次界外球,追軌跡才發現)。

## 2026-09-03:模擬遊玩的節奏與跑動 —— 錨在真實跑動量、衝刺、熱區與三路進攻

使用者回饋:比賽時間太快、跑動穿插太少,問有沒有場上跑動可以參考。有,而且比預期多:

| 資料 | 來源 | 用在哪 |
|---|---|---|
| 每隊每分鐘跑動距離、衝刺次數 | FotMob 追蹤資料(已在快取) | 無球跑動的頻率與幅度、衝刺比例 |
| 逐人場均跑動、最高速度 | 同上 | 個人勤勞度(跑得多的人多跑)、衝刺速度 |
| **逐人觸球熱區** | FotMob `heatmap` 端點(新探到):每人一串觸球座標,105×68 | 站位基準 = 陣型格與熱區質心各一半;離散度決定活動範圍 |
| **三路進攻佔比** | FotMob `attackingZones`(新探到):左/中/右,全場與上下半場 | 攻方整體往慣用那一側偏 |

拿不到的仍是逐秒軌跡;軌跡是演出,資料給的是量與區域,畫面上照這樣寫。

### 做法

- **時間尺度**:預設從每分鐘 0.16 秒(整場 14 秒)改成 2 秒(整場約 3 分鐘),加「真實時間」選項。
- **跑動排程**(`scheduleRuns`):攻方非持球員按細分角色起跑 —— 邊後衛套邊、邊鋒內切、中場前插、中鋒拉邊、中衛不跑;
  持續 2~4 秒;起跑率 × 該隊節奏(每分鐘跑動距離對聯盟均值)× 個人勤勞度(場均跑動對隊均);
  衝刺比例由該隊每分鐘衝刺次數決定。實測每格平均 1.1 人在跑、0.3 人衝刺(原本 0.55)。
- 熱區質心作站位基準,客隊鏡射 x(熱區是兩隊都向右進攻的座標,門將質心 x≈12 驗過)。
- 抓取器每場多一個請求(熱區),存 6×4 格計數 + 質心 + 離散度,不存逐點(逐點一季 24 MB)。

  畫面不會有任何錯。改叫 `pace`。

### 2026-09-02 覆查:三處修正

實際跑過之後改了三件事,原本的敘述有兩處講太滿。

**1「不會改變模擬結果」太強,已改成「不改變比分與進球排程」。**
實測 seed 1 的控球率 54.8% → 46.5%(另外三個種子完全相同)。原因不是避讓讀了
比分,而是:避讓改位置 → `toGoal` 變 → 快攻射門早一拍或晚一拍 → `chooseNext()`
少呼叫一次 → **rng 流錯位**,之後整條路徑就不同了。比分不受影響(模型排的,
24 個種子都演出 2 顆),但避讓不是完全惰性的,下一個人要知道。

**2「跑完整場時檢查球員最小間距」證明不了那句話。** `__animProbe()` 是呼叫當下
的快照,而測試跑完才叫一次 —— 它看的是**最後一格**。逐格量下來:全場最小間距
中位數 **0.11 m**(24 個種子,最大 0.26 m),5~9% 的畫格有球員疊在一起。
也就是說球員還是會穿過去,只是比以前少(壅擠畫格 24 個種子:無避讓
7.6~22.7%、有避讓 5.1~12.9%)。

**兩個分佈重疊,單一門檻分不開**,所以防線改放在**純函式**上(精確值、無門檻):
偏移垂直於連線、迎面兩人偏同一個世界方向、太遠不閃、背對著走不閃。
跑完整場那條降級成毛胚(壅擠畫格 < 20%),註解裡寫明它守得到什麼、守不到什麼。

**3 找到一條會隨時間飄的假紅。** `node scripts/test.mjs` 單獨跑全綠、`npm test`
會紅同一條。原因:`last = performance.now()` 是 mount 當下的牆上時間,而無畫布的
測試台自己從 `now = 0` 開始餵時戳 → **第一格的 `dt` 是負的**,位置往目標的反方向
跳一下,跳多遠取決於行程已經跑多久(實測等 0/200/800 ms → 最小間距
0.20/0.008/0.13,差 25 倍)。瀏覽器不會給比 mount 更早的 rAF 時戳,所以只在測試台
發作。兩邊都修:模組把 `dt` 夾在 `>= 0`(負的 frame delta 本來就沒有意義),
測試台的合成時鐘從 `performance.now()` 起算。修完同種子跑三種起步時間,
結果一致到小數第四位。

**還沒做的**:避讓只改「目標點」,而積分每格只走 k≈0.1,兩人目標交叉時仍會穿過去
—— 所以壅擠只降了一半。要真的不重疊得在**位置層**再兜一次底(積分之後推開),
繞行決定路線、間距修正兜底,兩者不衝突。列在補齊規劃。

## 2026-08-31：點火器 Worker + 比賽日迴圈「判斷不出來就收工」的修正

**起因**：規劃 Cloudflare Worker 時做的第一次乾跑（假 token、不會派送）就抓到
真的故障：AVL vs ARS 19:00 開球，19:10 時即時資料已 10 分鐘沒更新，而
`epl-matchday` 在 **19:00 整** 就「completed」結束了 —— 整場比賽零輪詢。

**根因**（不是 cron，也不是 `decideWindow`）：迴圈的收工判斷寫成
`if [ "$(… .active)" != "true" ]; then break`。那條管線只要有一點閃失
（輸出空、JSON 壞、`fixtures.json` 剛好被同一輪的 build 改寫到一半），
就會被當成「比賽都結束了」。拿當時的真實資料重跑 `decideWindow`，
它回的是 `active: true`。

- 兩支比賽日工作流程改為 **只有明確收到 `false` 才收工**；解不出來印 `unknown`
  並繼續跑。多跑一輪的成本，遠低於漏掉一場比賽。
- 新增 `infra/ignition-worker/`（Cloudflare Worker，進版控）：
  - **點火**：比賽快開打而沒有 job 在跑 → 派送比賽日迴圈。
  - **看門狗**：比賽正在踢而即時資料 > 6 分鐘沒更新 → 自動補派送；
    > 15 分鐘 → 送 webhook 告警。這是本站第一個會「主動說壞了」的機制。
  - **收工部署**：當天最後一場結束 30 分鐘後補一次完整建置與部署。
  - 無狀態（不用 KV，冪等靠「派送前先問 GitHub 有沒有 job 在跑」）；
    窗口故意比工作流程寬（95/155 對 75/140），因為它只是扳機，
    真正的判斷仍在 `live-window.mjs` —— **兩邊不是同一份邏輯，也不應該是**。
  - GitHub 原本的 cron 不拿掉，兩條路徑並存。
- 依據：實測前七天 `epl-matchday` 完全沒有 job 在跑的空窗中位數 43 分鐘
  （設定 15 分鐘）、只有 5% 在 20 分鐘內接上、最長一段 44 小時。
- 部署步驟見 `infra/ignition-worker/README.md`。**token 由使用者自己開**
  （fine-grained、只勾這個 repo 的 Actions: Read and write），本站不經手憑證。

## 2026-09-01:已完賽場次的「賽前機率」原本是事後算的(英超)

規劃盤點時查到的,比原本排在前面的事都重要。

`build.mjs` 的模型擬合在 `[...history, ...curPlayed]` —— **含本季已完賽的比賽**;
接著把那組機率掛到**每一場** fixture,包括已賽的。走查回測的逐場預測
(`backtest-matches.json`)只涵蓋跑完的賽季,**本季 0 場**,所以本季已賽場次
拿到的就是全資料模型的輸出。

而單場分析頁把它標成「**01・賽前模型**」,還據此下兩個結論:
「模型賽前最看好的就是這個結果」、「模型 vs 市場誰給實際結果的機率較高」。
Elo 是逐場更新的 —— 那場的比分直接進了參數。**不是編數字,是把數字標錯,
而結論是從錯的標籤長出來的。**

**西甲與英冠的 build 從第一版就拒絕這樣做**(`prediction: m.played ? null : ...`),
所以那兩個聯賽是對的,要修的是英超。

### 修法

`prob-history` 的每場**第一個點就是開賽前凍結的機率**(第 0 分,`m.preMatch`,
完賽後封存不再改)。抽出共用的 `preMatchSnapshots(store)`(三個聯賽同一份),
然後把欄位拆成兩個:

- `prediction` —— **只放真正的賽前機率**:未賽 = 目前模型;已賽 = 開賽前快照;
  拿不到就是 `null`。
- `postFit` —— 已賽場次「目前模型怎麼看」。是背景資訊,畫面上標明它不是賽前預測。

覆蓋率:英超 10/20、西甲 7/30(從 0),每個比賽日增加。**補不回過去的場次** ——
快照要開賽前抓得到即時樣本才有,本站這一季才開始存。

### 畫面

- 沒有快照時,「實際結果的賽前信心」與「三向機率並排」**整個不畫**,並說明
  為什麼:那兩張卡整張都是拿賽前機率做的推論。
- 賽前分頁對已完賽場次加一句話,並把小標改成「目前模型・非賽前預測」;
  有快照的話同一句話裡把真正的賽前機率寫出來。
- 快照只有 1X2(它是曲線的第 0 分點),沒有賽前 xG —— 那兩列顯示「—」,
  四個 xG 全空時整張卡不畫。
- **西甲的綜合對比因此活了**:改用跟英超同一個 `phaseComparison`,
  有快照就有完整比較(實測 RSO|ESP:賽前 46/25/28、市場 50/26/24、賽後 2:1)。

`npm test` 加八條(含「已賽場次的 prediction 一定是快照」「postFit 只出現在
已賽場次」「沒有快照時那兩張卡不畫」「兩個聯賽走同一個 phaseComparison」),
`test-laliga.mjs` 那條舊斷言跟著放寬成「null 或快照」並補一條「快照不含 xG」。

## 2026-09-02:新增「我的預測」——自己猜,賽季末跟模型與市場比

使用者要一個模式:一輪一輪自己預測比分與勝負、寫下理由,賽季結束看自己的勝率,

頁內自己選聯賽。計分抽成純函式 `predict-score.js`(零依賴,`npm test` 直接 import)。

### 四條界線,每一條都寫在畫面上

1. **完全不碰模型。** 預測只存在使用者自己的瀏覽器(localStorage),build 不讀、
   產物裡沒有、也不回饋進任何機率。測試守著:三支 build 都不得出現
   `predict-score` 或那個 storage key,`web/data/*.json` 裡也不得出現。
2. **開賽就鎖。** 開球時間一到輸入變唯讀。計分那層還有第二道(`isEligible`)——
   匯入別人的檔案也擋得住:`savedAt >= kickoff` 的紀錄不列入計分,並照實回報筆數。
   **賽後才填的不是預測,是回顧。**
3. **模型與市場的機率在按下儲存的當下就凍結進紀錄**,之後不重算。賽後重算的模型
   已經看過結果了 —— 這個專案昨天才為了同一件事修過一次(prediction / postFit)。
   鎖住的場次顯示的也是紀錄裡那一份,不是現在的。
4. **比較一律在同一批場次上做。** 市場盤口不是每場都抓得到,所以總表分兩組:
   「你 vs 模型」與「你 vs 模型 vs 市場」,各自標樣本數。

### 開發中抓到的一個會說謊的數字

兩場都沒有盤口,總表卻印「**市場 0.0%**」—— `marketHit` 是 `null`,而
`filter(null)` 算成 0 命中。那不是市場猜錯,是根本沒有市場。改成「整批都有才算」,
沒有就回 `null`,畫面寫「這批比賽沒有盤口,不是 0%」。
跟 `docs:check` 那條「**0 是一個看起來很像答案的數字**」是同一種錯。

### 指標

命中率(猜對勝負的比例)當主指標;另外附 RPS,而且講明**你的預測被當成 100%
押一邊**來算(你給的是斷言、模型與市場給的是機率),所以那個指標對你不利。
比分完全猜中另計。

### 順帶查到的資料現況

**未賽場次目前 0 場有市場盤口**(英超/西甲/英冠皆是)。`fetch-odds.mjs` 抓的
football-data.co.uk `fixtures.csv` 涵蓋的是**未來幾天**,repo 裡那份停在 08-31、
最後一場 09/01 —— 中間是國際賽週,第 3 輪(9/4 起)還沒進那個檔。
所以「跟市場比」在剛開始會有一段空窗,那是上游的涵蓋範圍,不是壞掉;
紀錄裡 `market: null` 會照實顯示「當時沒有盤口」。

### 資料放哪

localStorage 是**這台裝置這個瀏覽器**的東西:清網站資料、換瀏覽器、換裝置都看不到,
單檔版(warroom.html)是另一個來源、不共用。所以頁面上有匯出/匯入 JSON,
而且把這件事直接寫在畫面上,不要讓人以為它存在雲端。

## 2026-09-02:我的預測加開賽倒數與自動上鎖

使用者要求「倒數開始」。兩層:

- **這一輪的抬頭**:下一場截止還有多久(是哪一場)、還有幾場可以填、幾場還沒填。
  用「還沒開賽的場次裡**最早**的那一場」,不是「第一場」—— 這一輪可能已經踢掉幾場。
  全部開踢就整行不畫,不要留一個永遠 00:00:00 的倒數。
- **每一場**:截止倒數(= 開球時間)。走 `C.countdown` / `C.startCountdowns`,
  跟實時頁同一份,不另寫一個計時器。

### 上鎖是就地改那一張卡,不是整頁重畫

掃描每秒都在跑,而**重畫會把其他場次還沒按儲存的輸入洗掉**。所以越過開球時間時
只動那一張:停用輸入、拿掉儲存鈕、把「截止 …」換成「已開賽・鎖定」。
實測驗過:第 4 張鎖住的同時,第 1 張正在打的比分與理由原封不動、還能繼續編輯。

### 一個自己差點種下的坑

`render()` 每次切分頁、換聯賽、按儲存都會跑一次,而 `C.pageInterval` **不會**
收掉上一個(`startCountdowns` 自己會收,它不會)—— 不處理的話來回切幾次就變成
十幾個掃描同時跑。現在每次重畫先 `clearInterval` 舊的。

`npm test` 加四條,含「上鎖不得走整頁重畫」與「計時器要先收掉」。

## 2026-09-03:西甲賽後資料改由 FotMob 接手(SportMonks 取消後)

報告要的東西,而且多了 SportMonks 沒有的逐場 xG、shotmap、momentum。

### 做法:第三個 adapter,`buildProviderMatchReport` 一行都不用改

賽後報告吃的是**供應商中立的 canonical detail**,SportMonks 與 API-Football
各有一個 adapter。新增 `lib/adapters/fotmob-match.mjs` 是第三個,契約完全一樣,
所以發布邏輯、比分核對、烏龍球守門全部沿用。

**搬進 adapter 兩邊共用**(留兩份的話改了一邊另一邊會悄悄過期)。
抽完驗過 `official.json` **逐字元相同**。

抽的過程踩到一個:我把 `fotmobPos` 改成回 `GK/DEF/MID`,而原本是**單字母**

### 探測撈到兩個「照名字猜就會錯」的欄位

1. **Tackles 的 key 是 `matchstats.headers.tackles`**,不是 `tackles`。
   同一組裡 interceptions / recoveries / clearances 都是乾淨的 key,只有它是
   i18n 字串。猜 `tackles` 會拿到 0,而 0 看起來很像答案。
2. **事件的 `homeScore` / `awayScore` 對不上比分**(73 分那顆進球寫 0:0,
   終場 3-0)。語意沒驗證過,所以判得分方**不用它** —— 用 `isHome`,
   烏龍球再反過來,最後由既有的 `goalEvidence` 拿最終比分核對。

**烏龍球不掛射手**:`isHome` 指的是踢進的人屬於哪一隊,而得分的是對面。
球隊計數要算、射手不指名 —— 配錯人比不配對糟(本站反覆記過的同一條)。

實際上是我們沒有對照(跟賠率解析器「解不出來就把表頭印出來」同一個道理)。

`fetch-laliga-fotmob.mjs`:永久快取(完賽資料不會變,抓過就跳過)、單線、
間隔 400ms、每次最多 15 個請求;**比分跟本站賽程對不上就整場不收**。
`build-laliga` 讓 FotMob **排在 SportMonks 之後、只補它沒有的場次** ——
既有 30 場維持原來的來源,不因為換供應商就把核對過的資料重寫一遍。

新指令原本取名 `laliga:postmatch`,而那個名字**已經是 API-Football 那支的**

`laliga:fotmob-postmatch`,檔名也從 `fetch-laliga-postmatch.mjs` 改成
`fetch-laliga-fotmob.mjs`,免得跟 `fetch-postmatch.mjs` 混淆。

runner 上、跟著容器一起消失。

比「沒抓到」更糟的是:快取永遠是空的 → **每次執行都重抓同樣那 6 場**,

修:回寫清單加上 `epl/data/raw/fotmob-la-liga/`。

第一次跑完之後,抓取器把對映不到的 key 印出來,才看到真正的名字:

| 我猜的 | 實際 |
|---|---|
| `offsides` | **`Offsides`**(大寫開頭) |

同一份 payload 裡命名風格並不一致(有大寫開頭的、有加前綴的、還有一個是 i18n
字串 `matchstats.headers.tackles`)。**這就是為什麼對映不到要吵而不是靜靜顯示
「—」** —— 不吵的話這四個欄位會一直空著,而看起來像上游沒有。

逐人統計那一層同樣加了回報(`unmappedPlayerStats`),下一次執行會把還沒用到的

### 對著真實快取驗證,又抓到一個「0 看起來很像答案」

拿快取裡的 FotMob detail 實際產一份報告,跟同一場的 SportMonks 版逐欄位對照
(ALA 3-0 GET):陣型、先發 11、替補 5、進球 3、黃牌 4、射手三人、戰術解讀 3 條
**全部一致**,而且 FotMob **多了 xG 1.93**(SportMonks 那邊是 null)。

只有一欄對不上:**球場排數 FotMob 1 排、SportMonks 4 排**。

根因:我把 `xi[].grid` 留成 `null`,而 `rowsOf` 的實作是
`String(player.grid ?? '').split(':').map(Number)` —— **`Number('') === 0`**,
於是 11 個人全部落進「第 0 排」,球場圖會畫成一條線,**而且不會有任何地方報錯**。
這是本站記過的「0 是一個看起來很像答案的數字」的第三次。

兩層都修:

- adapter 依 `verticalLayout` 算出真正的 `grid`(「排:位」,跟 SportMonks 同格式)。
- `rowsOf` 硬化:空字串與 null 一律當成沒有站位資料,整份回 null 讓呼叫端退回 ——
  這是共用程式,任何供應商漏給 grid 都不該變成一條線。

### 逐人統計:四個欄位原本是空的

同樣對著真實資料修:`offsides` → `Offsides`(大寫)、對抗是 `duel_won` / `duel_lost`
兩個 key 要自己加、**逐人沒有「總射門」**這個欄位(只有射正/射偏/被封阻三個,
三個都在才相加,缺一個就留空 —— 湊不齊的和是錯的數,不是估計值)。

快取存的是**轉換後**的 detail(原始 payload 一場約 200 KB,整季會到七十幾 MB),
所以對映表改了之後舊快取不會跟著變 —— 加了 `--force` 重抓。

### 對映表版本:讓「要重抓」變成機制而不是「要記得」

快取存的是轉換後的 detail,所以每次修好欄位對映,舊快取都不會跟著變。
第一版的處理是加一個 `--force` 旗標 —— 但那要人記得,而記得不是機制。

改成 adapter 匯出 `ADAPTER_VERSION`,每筆快取記下產生它的版本;抓取器把
版本不同的場次自動列入待抓,並在 log 講明「其中 N 場是對映表改版要重抓的」。
受每次請求上限節制,不會一次全打。**改了欄位對映就把版本 +1**,寫在常數旁邊。

### FotMob 轉換的回歸測試(17 條)

用**合成 payload** 測,不依賴快取狀態 —— 欄位形狀是探測出來的真東西,
測試守的是轉換不要走樣。這一層會出的錯**都不會拋例外**:欄位名猜錯 → 那一欄
靜靜是 null;grid 給 null → 十一個人被畫成一條線;烏龍球掛到踢進的人身上 →
配錯人。掃原始碼掃不出這些,所以要真的轉一遍再看結果。

守的東西:實測過的 key(`Offsides` 大寫、`keeper_saves`、`shot_blocks`)、
沒見過的 key 要回報不要吞、分隔列不算數據、逐人總射門是三個相加、
對抗是 won+lost、Tackles 的 i18n key、牌從事件補、**烏龍球算給對面而且不掛射手**、
半場與文字評論不進時間軸、**先發要有真正的 grid**(4 排不是 1 排)、
轉出來的 detail 過得了賽後報告守門、比分對不上不發布、位置代碼是單字母。

**版本數字只回報不當紅線**:舊快取是加 `adapterVersion` 之前寫的,抓取器會自己
重抓,紅在這裡只會變成沒有人看的紅(`docs:check` 那條「會漂移的只回報、
人為改動才擋」的同一個分界)。當紅線的是**機制** —— 抓取器必須真的比對版本。

## 2026-09-03:手機版面 —— 導覽列吃掉三成螢幕、盃賽頁整頁橫向捲動
