# 英超／西甲戰情室(PL & La Liga War Room)

以英超為主的比賽分析平台；另有西甲的**總覽、賽程預測、球隊、球員與戰術摘要**。所有畫面都只呈現已取得的真實資料。

> **要接手開發?** 先看 `../CLAUDE.md`(工作規則與踩過的坑)、
> `docs/接手資訊.md`(這個時間點的狀態)與
> **`docs/補齊規劃.md`(接下來做什麼、什麼不要做、哪些路已經試過而不通)**。

免安裝套件、免打包工具 —— 只要有 Node 18+,三行指令就能在本機跑起來。
(程式碼沒用到 Node 18 之後才有的 API;CI 與開發環境跑的是 22。)

```bash
cd epl
npm run fetch     # 抓原始資料(已附在版控裡,首次可略過)
npm run build     # 跑分析引擎,產生前端資料集
npm run serve     # 開 http://localhost:5173
```

西甲使用獨立資料目錄，不會覆蓋英超。抓取與建置方式：

```bash
npm run laliga:fetch    # 只抓 2025-26、2026-27 兩季
npm run laliga:crests   # 抓本季 20 隊隊徽並縮圖內嵌（首次／換季執行）
npm run laliga:setpieces # 抓上一季 20 隊 xG、射門、陣型與進球情境（首次／換季執行）
npm run laliga:players   # 抓上一季球員摘要（已有快取時跳過）
npm run laliga:postmatch # 只補尚未快取的完賽統計、正式陣容、事件與球員評分
npm run laliga:build    # → web/data/leagues/es1/
npm run serve           # 頁首可在英超／西甲間切換
```

西甲目前支援賽程、積分榜、近期戰績、歷來交手、球隊逐季資料、Poisson + Elo 預測、可取得的市場去水機率，
以及上一季球隊 xG/xGA、射門、實際使用陣型、進攻速度、五種進球情境、風格雷達、球員進攻摘要和戰術摘要頁。
完賽場次在完整欄位與正式比分都核對通過後，會顯示球隊統計、正式陣容、事件與逐球員評分；
西甲戰術摘要只使用 Understat 整隊統計；逐場官方先發、球員站位與攻守形狀仍未接入，頁面不會拿英超資料代替。

想寄給別人、或不想開伺服器?打包成單一 HTML 檔,直接雙擊就能看:

```bash
npm run bundle    # → dist/warroom.html(約 12 MB,含兩聯賽資料、隊徽與字體,零外部請求)
```

**想看進行中的比賽,用即時模式**(一個指令搞定,不用反覆重建):

```bash
npm run live:watch    # 服務網站 + 背景輪詢官方 API,頁面每分鐘自己更新
```

### 本機優先／一次發布模式

日常開發與比賽日改由本機執行，不讓 GitHub Actions 的排程與高頻工作搶 runner。
啟動英超與西甲的本機即時模式：

```bash
export SPORTMONKS_TOKEN=...  # 西甲即時快取需要；只留在本機終端，不會寫入檔案
npm run local:watch          # 英超每 60 秒；西甲每 120 秒，兩者皆不會 git push
```

準備發布前，用一次同步把最新即時快照寫回本機並重建兩聯賽資料集：

```bash
npm run local:sync            # 英超 + 西甲即時快照（西甲最多 2 次請求）→ build
git diff --stat               # 檢查變更
git add . && git commit       # 確認內容後才做
git push                      # 最後一次上傳
```

`local:sync` 不會執行賽後大批量補抓，也不會自行提交或推送；Token 只從目前終端環境讀取。

本機即時模式的健康檢查頁為 `http://localhost:5173/api/live-status`，會同時列出英超與西甲
最後輪詢時間、錯誤狀態與輪詢間隔；這個頁面不會觸發 API 請求。

同一個 Wi-Fi 的其他裝置可開 `http://<這台電腦的區網 IP>:5173`。完成一段工作後，
才以 `git add`、`git commit`、`git push` 一次上傳；GitHub 的資料更新／Pages 部署工作流程
已改為 **Actions → Run workflow** 才會執行，避免每次 push 又佔用遠端佇列。

或手動抓一次:

```bash
npm run live      # 官方 FPL API,比賽進行中逐分鐘更新
npm run season    # 本季每一輪的逐球員資料(排行榜的「本季」分頁靠它)
npm run build     # 併進網站
```

第一次跑或換季時,再抓一次隊徽:

```bash
npm run crests    # 27 隊隊徽 → 縮圖 → 內嵌成 data URI
```

## 本季 vs 上季

球員數據一律**分成兩套**,不會混在一起:

| | 來源 | 何時有 |
|---|---|---|
| **上季** | 該季的完整 FPL 統計 | 一直都有 |
| **本季至今** | `npm run season` 抓的每一輪逐球員資料累加 | 該輪結束、上游發布之後 |

球員頁上方可以切換,排行榜、表格、雷達圖都會跟著換,標題也會標明是哪一季。
賽季剛開打時本季沒有數據是正常的 —— 頁面會直接說明原因和補資料的指令,而不是默默拿上季的數字充數。

排行榜的門檻(例如「終結超出期望」要求的 xG 下限、CP 值要求的出場時間)會依賽季已進行的比例縮放,
不然開季前幾輪永遠是空的。

轉會球員的上季數據掛在**當時效力的球隊**,排行榜會標示「上季 XXX → 本季 YYY」。

## 已完賽的比賽

賽程頁可以切換賽季。選過去的賽季就會看到:

- **比分**與該場的賽前機率
- **模型有沒有命中**(賽前機率最高的結果 vs 實際結果)
- 點進去有**完整賽前／賽後對比**:賽前模型、市場去水機率、最終比分與真實 xG 同尺度比較,
  並可切換查看雙方實際先發與陣型、換人時序、門將表現、自動生成的戰術解讀
- 「專業市場機率」代表盤口去水後的市場定價共識,**不是資金流向**,不會推論大戶實際投注金額

賽前預測是 `npm test` 跑走查回測時順便存下來的(`data/backtest-matches.json`)——
每一場都只用開賽前的資料建模,所以「命中率」是誠實的。

## 實時戰況怎麼運作

### 先講清楚:什麼情況下看得到即時比分

即時比分要連得到**官方 FPL API**(`fantasy.premierleague.com`)。能不能連得到,取決於你在哪裡跑:

| 執行方式 | 即時比分 | 說明 |
|---|---|---|
| **`npm run live:watch`(自己的電腦)** | ✅ 有 | 背景每分鐘輪詢,頁面自己更新。**要看即時比分就用這個** |
| **GitHub Actions + Pages** | ✅ 可手動發布 | 只在本機完成後手動執行，避免高頻工作佔用 runner |
| 單檔版 `warroom.html` / 發布出去的頁面 | ❌ 沒有 | 為了安全,這類頁面不允許對外請求,只能顯示打包當下的資料 |
| 受限網路的開發環境 | ❌ 沒有 | 例如只放行 GitHub 的沙箱 |

### 沒有即時資料源時,頁面仍然知道「現在有比賽在踢」

這一段**完全不需要任何即時資料源**,只靠賽程表與現在時間:

- **進行中**:開賽時間已過、還在 115 分鐘窗口內的比賽,會標出「開賽後約 N 分鐘」並顯示賽前預測,
  同時明講「比分需要即時資料源」——不會假裝知道比分
- **等待賽果**:時間上早該結束、但資料源還沒給比分的比賽
- **開賽倒數**:尚未開賽的比賽

頁面每 30 秒自己重畫一次,所以比賽會自動從「倒數」變成「進行中」再變成「等待賽果」,不用手動重整。

### 三種資料來源

| 來源 | 指令 | 更新頻率 | 限制 |
|---|---|---|---|
| **官方 FPL API** | `npm run live -- --source=api` | 比賽進行中**逐分鐘**更新 | 需要能連到 `fantasy.premierleague.com` |
| **GitHub 鏡像** | `npm run live -- --source=mirror --round=N` | 每輪賽後 | 不會場中更新 |
| **重播** | `npm run live -- --replay=2025-26:1` | — | 真實的歷史比賽,網站會標示「示範模式」 |

`npm run live` 預設是 `--source=auto`:先試官方 API,連不到就自動改用 GitHub 鏡像。

### 完賽球員評分與完整攻守數據

英超的球員／賽後主要資料改由 `SPORTMONKS_TOKEN` 同步；設定後執行 `npm run sportmonks:sync -- --league=pl`，
資料會先寫入本地快取，建置時優先採用 SportMonks。FPL 仍負責英超表現統計與即時賽程鏡像。

設定 `API_FOOTBALL_KEY` 後，英超的 `npm run live` 與西甲的定時流程會在確認完賽後補抓一次 API-Football 的球隊統計（作為 SportMonks 缺口備援）、
球員 0–10 評分、射門、傳球、關鍵傳球、傳球成功率、對抗、盤帶、鏟球、抄截、攔阻、犯規、
門將、正式陣容與完整事件時間軸。西甲另要求供應商比分與 openfootball 正式比分完全一致；所有必需欄位都齊全才寫進
`data/raw/api-football-la-liga/2026-27-match-details.json` 永久快取；
同一場後續輪詢不再呼叫 API。若供應商剛完賽尚未補齊，至少隔 30 分鐘才重試，且每場每天最多三次。

```bash
export API_FOOTBALL_KEY=xxxx
npm run postmatch       # 手動補抓本季所有尚未快取的完賽場次
npm run laliga:postmatch # 西甲；目前一輪通常只需「完賽清單 + 批次詳情」2 次請求
npm run build
npm run laliga:build
```

金鑰只存在 Node 執行環境，不會寫入 JSON 或前端。API-Football 不提供速度、跑動距離與衝刺資料，
介面會明確標示不可用，不會由其他欄位估算。

### 一次發布(GitHub Actions)

`.github/workflows/epl-live.yml` 現在只在 **Actions → Run workflow** 時執行。建議先在本機更新並驗證，
再一次推送與發布；GitHub runner 仍能連官方 FPL API，但不會自行高頻輪詢:

1. **把抓到的即時資料提交回 repo**(`epl/data/raw/live.json` 等,帶 `[skip ci]` 避免遞迴觸發)。
   之後在任何環境只要 `git pull` + `npm run build`,就是最新比分。
2. **部署到 GitHub Pages**(需要先啟用,見下)。

**啟用 Pages(只需做一次)**:Settings → Pages → Source 選 `GitHub Actions`。
> 為什麼不能自動開:工作流程預設的 `GITHUB_TOKEN` 沒有「建立 Pages 站台」的權限
> (`Resource not accessible by integration`),這是 GitHub 的限制。
> 在還沒啟用之前,工作流程會自動偵測並**略過部署**,不會讓執行失敗。

啟用後網址是 `https://<帳號>.github.io/<repo>/`,單檔版一併放在 `/warroom.html`。

目前三個資料／比賽工作流程都保留 `workflow_dispatch` 作為遠端備援，沒有 schedule 或 push 觸發；
需要遠端抓取時才在 Actions 手動執行。

### 比賽進行中拿得到什麼

| 顯示的東西 | 資料怎麼來的 |
|---|---|
| 即時比分、進行分鐘 | 來源的 fixture 狀態 |
| **實際排出的先發十一人與陣型** | 出場紀錄中 `starts=1` 的球員,依位置統計人數 |
| 與該隊常態的差異 | 對照上季的人力配置(例如「後場比上季常態多 0.9 人」) |
| **換人時序** | 由出場分鐘反推(替補打 30 分鐘 ≈ 第 60 分鐘上場),標示 ≈ 為推估 |
| 場上 xG / xA | 各球員的期望進球加總 |
| **即時勝率** | 賽前 λ 依剩餘時間等比例縮放,代入目前比分做卷積;紅牌會調整雙方強度 |
| 下一球歸屬機率 | 兩個 Poisson 過程的強度佔比 |
| 門將表現 | 撲救次數、期望失球 vs 實際失球 |
| 自動戰術解讀 | 由陣型差異、xG 與比分的落差、換人時機、紅牌等條件生成 |

**沒有的東西,不會假造**:FPL 的資料沒有進球與卡牌的**發生分鐘**,所以事件不會標時間軸;
「陣型」是依 FPL 位置分類統計先發人數,邊鋒會被算進中場,不等於轉播圖上的陣型。

### 即時積分榜

本季積分榜同時吃兩個來源:openfootball 的正式賽果,以及即時來源裡「已完賽」的場次。
上游還沒更新時,即時來源的結果會先補進去,所以積分榜不用等。

### 開賽倒數

倒數用的是 **FPL 的 UTC 開球時間**,不是 openfootball 的預設時段 —— 後者有 32 場的日期與實際不符
(電視轉播改期)。時間一律換算成觀看者所在時區顯示。倒數不需要任何即時資料,永遠可用。

## 分析引擎

### 1. 比賽預測:Dixon-Coles Poisson + Elo

每隊各有進攻強度 `att` 與防守弱點 `def`,加上聯盟基準 `μ` 與主場優勢 `γ`:

```
λ主 = exp(μ + att主 + def客 + γ)      λ客 = exp(μ + att客 + def主)
```

- **時間衰減**:越近期的比賽權重越高(ξ = 0.0035/天,約半年半衰)
- **低比分修正 ρ**:Dixon-Coles 的 τ 修正,補足獨立 Poisson 低估和局的問題
- **升班馬先驗**:沒有近期英超樣本的球隊,套用「聯盟後段」強度,並在模擬時給更大的不確定性
- **Elo**:同時跑一套含進球差加權、跨季回歸平均的 Elo 評分

### 2. 為什麼最後採用「兩者平均」

`npm test` 會跑**走查回測**:重跑上季 38 輪,每一輪都只用開賽前的資料重新建模再預測,絕不偷看未來。

| 模型 | RPS ↓ | LogLoss ↓ | 命中率 ↑ |
|---|---|---|---|
| Dixon-Coles Poisson | 0.2084 | 1.0268 | 47.9% |
| Elo | 0.2085 | 1.0264 | 47.1% |
| **兩者平均(採用)** | **0.2076** | **1.0237** | **48.7%** |
| 基準線(固定 44/25/31) | 0.2274 | 1.0808 | 42.6% |

平均之後三項指標都最好,所以平台顯示的機率用平均值,單場頁面同時列出兩套模型各自的看法。

### 3. 賽季模擬

用預測強度把剩餘賽程跑一萬次。關鍵細節:**每一次模擬都重新抽一組「球隊真實強度」**
(有樣本的隊 σ=0.10,升班馬 σ=0.15,並扣掉 σ²/2 讓期望值不偏),
否則只用點估計會嚴重低估不確定性,模型會過度自信地把冠軍發給某一隊。

### 4. 戰術指標怎麼算的

| 指標 | 算法 |
|---|---|
| 人力配置(如 `4.6 - 4.3 - 1.1`) | 各位置出場分鐘 ÷ 外場總分鐘 × 10 = 平均場上人數。**注意 FPL 把邊鋒歸類為中場**,所以這是人力分佈不是轉播圖陣型;後場接近 5 = 三中衛/五後衛體系 |
| 球隊 xG | 全隊球員期望進球加總 |
| 球隊 xGA | 該隊**門將**的期望失球(xGC)加總 |
| 終結超出期望 | 實際進球 − xG,正值代表終結超常(通常難延續) |
| 門將撐場 | xGA − 實際失球 |
| 領先保分率 | 半場領先的比賽中,實際拿到的分數 ÷ 可能的最高分數 |
| 下半場增減 | 下半場淨勝球 − 上半場淨勝球 |
| 定位球威脅 | Understat 的非十二碼定位球 xG ÷ 場次(角球 + 其他定位球 + 直接任意球),再轉為 20 隊百分位 |
| 主力吃重度 | 出場最多的 11 人佔全隊總出場的比例 |

### 5. 標準陣型:把 FPL 的四類細分成八種角色

FPL 只把球員分成 GK/DEF/MID/FWD,而且**把邊鋒歸類為中場**。光看「五名中場」
分不出那是三中場加兩邊鋒,還是五個中路球員 —— 那是完全不同的球隊,
也推不出 4-2-3-1 或 4-3-3。

所以先用 per-90 的產出側寫把每個人細分成
**中衛 / 邊後衛 / 防守中場 / 中場 / 前腰 / 邊鋒 / 中鋒**:

| 角色 | 資料上的特徵 |
|---|---|
| 邊鋒 vs 防守中場 | 每 90 分鐘威脅值約 **30 vs 7**,解圍攔截 **1 vs 3.5** |
| 中衛 vs 邊後衛 | 解圍攔截 **8 vs 3.5**,創造力 **4 vs 20** |
| 前腰 vs 邊鋒 | 威脅值百分位 **61~77 vs 90~98**;助攻取向偏前腰 |

差距是數倍不是勉強分得開。用聯盟內百分位而非絕對數字,才不會跨季失準。
**已用 15 位位置明確的球員驗證,全部分類正確**。

再由各角色的**出場分鐘**推導常態陣型(跟人力配置同一個做法,只是粒度更細),
兩條慣例決定寫法:三中衛時邊後衛算翼衛歸中場線(3-5-2 而非 5-3-2);
沒有前腰時邊鋒與中鋒同排(4-3-3 而非 4-3-2-1)。

**攻守分型**是推論而非實測:我們沒有球員追蹤資料,做不到真正的有球/無球站位。
只用兩條可驗證的規則 —— 創造力排在同角色前段的邊後衛進攻時前壓、
防守貢獻排在同角色前段的邊鋒無球時退回中場線。

> 樣本不足就不推導。升班馬上季在英冠,可能只有兩三名球員有英超紀錄,
> 用三個人推「這隊平均擺幾個中衛」會得到 0-7-3 這種不存在的陣型。
> 目前 17 隊可推導、3 隊標示資料不足。

### 6. 球員百分位

同位置、上季出場 **600 分鐘以上**的球員為母體,各位置有專屬的六軸雷達
(門將看撲救與零封、後衛看防守貢獻與解圍、中場看創造與威脅、前鋒看進球與終結)。

> **轉會處理**:上季數據掛在**當時效力的球隊**,不會算到新東家頭上;
> 排行榜與球員卡都會標示「上季 XXX → 本季 YYY」。

## 資料層:Canonical Schema + adapter

所有外部資料一律先經 adapter 轉成 `lib/canonical.mjs` 定義的格式,之後的分析、模型、
AI、前端都只讀這個格式,**永遠不直接讀供應商的 JSON/CSV**。

為什麼值得這樣做:未來要接歐冠、英國盃賽,或從免費源換到付費源(Opta/StatsBomb)時,
只需要寫一個新的 adapter,上層一行都不用改。反過來說,只要有一個指標偷偷去讀了供應商欄位,
這個保證就破了。

賽事定義帶著旗標,模型行為跟著旗標走:

```js
'eng.1': { type:'league', extraTime:false, penalties:false, twoLegged:false, crossLeague:false }
// 之後要加的:
// 'uefa.cl': { type:'europe', extraTime:true, penalties:true, twoLegged:true, crossLeague:true }
```

淘汰賽要算加時與 PK、兩回合要用總比分晉級、跨聯賽要做 Elo 校準 —— 這些都不是「多抓一份賽程」
就能解決的,所以旗標先寫進契約,實作再逐步補上。

## 文字分析怎麼產生(AI 報告層)

**核心原則:數字先算完,文字才生成。語言模型只負責解讀,不負責計算,也不負責記憶。**

```
分析引擎 ──► feature bundle ──► 沒有 API key ─────────────► 模板版(永遠可用)
                    │
                    └► 有 key ──► 雜湊命中快取? ──是──► 直接用(不花錢)
                                        │否
                                        ▼
                                   LLM 產出 ──► 數字驗證 ──不過──► 退回模板版
                                                       │過
                                                       ▼
                                                    寫入快取
```

**1. feature bundle** —— 一場比賽所有可被引用的數字,由既有的分析引擎算完、四捨五入定案。
每個數字都有 id、人看得懂的名稱,以及「允許寫進文章的字面形式」。

**2. 模板引擎** —— 純函式,沒有 API key 也一定產得出完整報告。它是基準線而不是備胎:
模板寫得出來的東西,LLM 就沒有加分空間。

**3. 數字驗證** —— 文章裡出現的每一個數字,都必須能在 bundle 的 facts 找到對應
(含四捨五入與百分比寫法的容差)。找不到就是模型自己編的,**整篇退回改用模板版**。
另外還會擋掉 bundle 根本沒有的主題(傷兵、轉會、天氣、裁判、賠率)。

這比「叫模型不要亂編」可靠得多,因為它不靠模型自律,是事後可驗證的硬檢查。
`npm test` 會把全站 381 篇模板文章逐篇跑一次驗證,並用一個「會編數字的假模型」
確認退回機制真的會觸發。

**4. 快取** —— 以 bundle 的內容雜湊為鍵,資料沒變就不重打 LLM。
只有 LLM 的產出進快取:模板是純函式,重算不用錢也不會變,
把它快取起來反而會出事(改了模板、雜湊沒變,舊文字就會一直被端出來)。

啟用方式:設好 `ANTHROPIC_API_KEY` 再跑 `npm run build`。沒設就是模板版,內容一樣完整。
**API key 只在建置階段(Node)使用,產物是靜態 JSON,key 不會、也不可能出現在前端。**

### 真人名宿／專家觀點是另一條資料管線

真人觀點不由 LLM 生成,也不從上面的 feature bundle 推測。人工核對後寫進
`data/manual/expert-opinions.json`,每筆必須有具名專家、身分、媒體、發布時間、HTTPS 原始連結與改寫摘要。
`verified:false` 可留作草稿但不會送到前端;缺欄位、錯比賽、重複來源與直接引言都會讓 build 失敗。

前端的「名宿／專家觀點」與「本站 AI／模型分析」是兩個獨立區塊。沒有核對來源時就顯示 0 筆,
不會把模板文字冒充真人發言。完整填寫方式見 `docs/專家觀點-資料格式.md`。
使用者開頁只讀 `experts.json`,不會搜尋媒體或呼叫任何 API。

## 需要人工維護的部分

**教練名冊**是唯一沒有免費穩定 API 的部分,`data/manual/coaches.json` 要靠手動更新:

```jsonc
{ "team": "ARS", "name": "Mikel Arteta", "zh": "阿爾特塔", "nat": "西班牙",
  "confidence": "high",              // high / medium / low / unknown,會顯示在頁面上
  "formation": "4-3-3",
  "style": ["高位壓迫", "定位球武器化"],
  "spells": [{ "from": "2019-12-20", "to": null }] }   // to = null 代表在任中
```

只要 `spells[]` 的日期填對,**戰績是自動算的** —— 系統會用日期切分比賽,
算出每位教練(含賽季中途接手者)任內的場次、勝率與場均勝點。
名冊整理時點記在 `_asOf`,頁面上會顯示鮮度提醒與每筆資料的可信度標籤。

## 已知限制(都寫在頁面上,不藏)

- 模型只吃比賽結果與 FPL 統計,**不含轉會、傷病、賽程密度的人工調整**。夏窗大手筆補強不會反映在強度上。
- 賽季模擬用獨立 Poisson 抽樣,和局會略少於真實比例(整季總積分約高估 1%)。
- 升班馬沒有近期英超樣本,用「聯盟後段先驗」估計,不確定性明顯較大。
- 「陣型」是用出場分鐘推估的人力配置,不是實際戰術板陣型(FPL 把邊鋒算中場)。
- 進球方式是上一完整賽季的球隊級統計;可分運動戰、角球、其他定位球、直接任意球與十二碼,但不把類型掛到個別球員的某一球。
- 外部新聞 RSS 需要能連到 BBC / Sky / Guardian;受限網路環境抓不到時會自動跳過,
  動態頁仍有傷停、轉會、賽前看點與數據敘事。
- **逐分鐘的即時比分需要官方 FPL API**(見上方表格哪些情況拿得到)。拿不到時頁面仍會依賽程
  標出哪些比賽正在進行,但明講比分未知,不會把非即時的資料講成即時。
- 「開賽後約 N 分鐘」是**開賽至今的實際時間**(含中場休息),不是比賽時鐘的分鐘數 ——
  沒有即時資料源就不可能知道現在是第幾分鐘,所以不假裝知道。
- 即時勝率假設進球速率在場上均勻分佈(實際上傷停補時略高),紅牌影響用的是經驗係數
  (該隊進攻 ×0.72、對手進攻 ×1.30),不是從本聯盟資料擬合出來的。

- 文字分析**只會講 feature bundle 裡有的數字**。所以它不談轉會八卦、更衣室氣氛、教練嘴仗 ——
  那些我們沒有資料,而寫進去就會被數字驗證擋下來。
- 沒有設 `ANTHROPIC_API_KEY` 時,分析文章是模板產生的:資訊完整但句式制式。
  這是刻意的取捨 —— 寧可句子呆板,也不要一個沒人檢查過的數字。

**預測數字僅供分析參考,不構成任何投注建議。**

## 兩種執行模式

同一份程式碼支援兩種模式,靠 `core.js` 的路由抽象切換:

| | 多頁模式 | 單檔模式 |
|---|---|---|
| 進入點 | `web/index.html`(需伺服器) | `dist/warroom.html`(可直接開) |
| 連結 | `teams.html?code=ARS` | `#teams?code=ARS` |
| 資料 | `fetch('data/*.json')` | 內嵌於 `window.__DATA__` |
| 倒數計時 | 兩者相同,純前端計算,不需要伺服器 | |
| 字體 | `fonts.css` 的 data URI | 同上,一併攤平進單檔 |

寫程式時一律用 `C.link(page, params)` 與 `C.go(page, params)`,不要寫死 `.html` 連結,
兩種模式才會同時正確。
